# 任务执行标准流程（Txx）

执行 `docs/开发任务清单.md` 中的任务（编号 Txx）时按以下流程；已有明确授权的方案连续执行，不逐单重复确认。编排职责以 [代理协作与执行](../../../docs/约定/代理协作与执行.md) 为准，验证以 [工程验证说明](../../../docs/约定/工程验证说明.md) 为准，本技能不另立全量测试口径。

## 第 0 步：读取任务所需上下文

1. 根目录 `AGENTS.md` —— 产品核心硬性规则、执行方式与专题入口。
2. `docs/技术架构与实施方案.md` —— 只精读与当前任务相关的章节（任务条目里引用了 §x.x）。
3. `docs/开发任务清单.md` —— 当前任务条目 + §0.3 全局固定约定 + 「依赖」任务是否已完成。

同一阶段已读取且未变化的内容不重复通读；交接给新会话时提供章节和当前状态。依赖未完成的任务不得开始（清单显式例外除外）。

## 第 1 步：先出计划，等用户确认

未经授权的多步任务列出三样东西并等用户确认；已经明确授权的方案按授权执行：

- 要新建/修改的文件清单（含测试文件）
- 实现步骤（按提交粒度拆分）
- 要写的测试点

步骤复杂时可用已发现的 `writing-plans` 技能成稿，不得虚称运行未发现的技能。

## 第 2 步：建分支

```bash
git switch -c codex/Txx
```

先检查工作区归属，复用适合的独立分支；共享活动工作区不直接切分支。验收通过后按授权交付到 `v2`，小步提交，`main` 仅按明确发版要求处理。

## 第 3 步：实现

- 遵守 AGENTS.md 全部产品核心硬性规则，特别是：契约优先（先改 `packages/contract` 的 Zod schema）、TS strict 禁 any、不新增技术栈清单以外的依赖、不用 CDN、UI 文案中文/标识符英文。
- 解析器或判分逻辑的改动：先补测试用例，再改实现。
- 默认测试先行：其余任务同样先写失败测试再写实现（AGENTS.md「开发流水线与完成标准」第 2 步）；纯样式、文案和文档可豁免，但要说明理由。
- 既定范围内的可逆实现选择自行处理；改变产品行为、数据或交付范围的重大决策再与用户对齐。

## 第 4 步：分层检查并保留真实证据

```bash
# 开发 / 修复检查点
pnpm test:quick
pnpm typecheck:affected
pnpm lint:changed
# 实现收口 / 验证单（已有有效结果不重复）
pnpm test:affected
pnpm e2e:affected
```

先按工程验证说明选择适用档位，不把以上命令每轮全部重跑。命中兜底时执行脚本决定的全量；不另加整仓单测、双浏览器或构建重复 PR CI。纯文档可豁免应用测试，说明理由并检查链接、镜像与 diff。改 E2E TS 时补其定向类型检查。

报告命令、版本/基线、范围、数量和退出码，完整日志落盘，对话只给摘要。零用例、dry-run 或只有 Tests passed 都不等于通过；提交后 `test:quick` 可能为空，不拿它覆盖提交前未测改动。失败先查具体证据、定点复现，不重跑到绿。

## 第 5 步：质量闸门（合并前必须过）

按 [OwnClass 代码审查技能](../../../.agents/skills/ownclass-code-review/SKILL.md) 固定本次任务的完整 diff，依次完成简化、正确性和适用的安全审查，再进入验收。

## 第 6 步：逐条对照验收

把任务条目里的「验收」逐条列出，每条说明：如何验证的（测试名、命令输出、或需要人工）。不允许笼统地说"验收通过"。

## 第 7 步：更新进度表

在 `docs/进度表.md`（全阶段总进度表）更新任务状态，证据写入对应验收记录。只有验收全部通过（含 🧑 项）才打勾；未验证项如实保留。阶段完成写交接并收口，不把后续跨层工作无限续给同一代理。

## 第 8 步：列出 🧑 人工验证项

带 🧑 标记的验收项需要用户本人手动检查（尤其 iPad 真机）。任务结束时单独列一节"需要你手动验证"，写清每项的操作步骤。没通过之前不要声称任务完成。
