# 任务执行标准流程（Txx）

执行 `docs/开发任务清单.md` 中的任何一个任务（编号 Txx）时，严格按以下顺序。不要跳步，不要把多个任务合并执行。

## 第 0 步：读三份文档（每次任务开始都要重读）

1. 根目录 `AGENTS.md` —— 硬性规则与常用命令。
2. `docs/技术架构与实施方案.md` —— 只精读与当前任务相关的章节（任务条目里引用了 §x.x）。
3. `docs/开发任务清单.md` —— 当前任务条目 + §0.3 全局固定约定 + 「依赖」任务是否已完成。

依赖未完成的任务不得开始（例外见清单末尾：T2.7 只依赖 T0.4，可提前）。

## 第 1 步：先出计划，等用户确认

列出三样东西后**停下来等用户回复"确认"**，不要直接动手：

- 要新建/修改的文件清单（含测试文件）
- 实现步骤（按提交粒度拆分）
- 要写的测试点

这是清单 §0.1 的硬性要求。计划本身就是一次对齐，避免实现方向跑偏后返工。

## 第 2 步：建分支

```bash
git checkout -b task/Txx
```

一个任务一个分支，验收通过后合并到 `v2` 分支。小步提交，每个提交保持可构建、测试通过。

## 第 3 步：实现

- 遵守 AGENTS.md 全部硬性规则，特别是：契约优先（先改 `packages/contract` 的 Zod schema）、TS strict 禁 any、不新增技术栈清单以外的依赖、不用 CDN、UI 文案中文/标识符英文。
- 解析器或判分逻辑的改动：先补测试用例，再改实现。
- 遇到文档未覆盖的设计决策：**停下来问用户，不要自行假设**。这是最常被违反的规则。

## 第 4 步：跑检查并贴出真实输出

```bash
pnpm lint && pnpm typecheck && pnpm test
# 涉及 E2E 的任务再加：
pnpm e2e
```

把命令输出贴在回复里，不允许只写"通过"。任何一项失败都视为任务未完成，先修再继续。

## 第 5 步：逐条对照验收

把任务条目里的「验收」逐条列出，每条说明：如何验证的（测试名、命令输出、或需要人工）。不允许笼统地说"验收通过"。

## 第 6 步：更新进度表

在 `docs/开发任务清单.md` §7 进度表中，把该任务从 `☐Txx` 改为 `☑Txx`。只有验收全部通过（含 🧑 项）才打勾；🧑 项未验证时保持 ☐ 并注明剩余项。

## 第 7 步：列出 🧑 人工验证项

带 🧑 标记的验收项需要用户本人手动检查（尤其 iPad 真机）。任务结束时单独列一节"需要你手动验证"，写清每项的操作步骤。没通过之前不要声称任务完成。
