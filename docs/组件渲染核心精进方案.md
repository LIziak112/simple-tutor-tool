> 日期：2026-10-06 定稿；2026-10-08、2026-10-09 修订。
> 读者：项目作者与后续接手的开发者（含 AI）。
> 与既有文档的关系：承接本地历史文档《组件渲染核心评审与改进建议》（归档名称，未纳入本次提交）的 §5–§8，增补 [技术架构与实施方案](技术架构与实施方案.md) 的 §5.1.1 与 §5.9。执行清单：[Phase7任务清单.md](Phase7任务清单.md)，任务口径与本文冲突时以本文为准。
> 结论：三层渲染架构的"展示"维度设计正确；行为维度（交互、判分、能力）分散在三处手抄镜像里。精进方向是能力化与能力包，不做运行时第三方代码插件。

## 一、结论

1. **架构脊梁维持**：三层架构（注册表 L1 → 宿主标签 L2 → React 组件 L3）与"原文即真相、展示时再解析"是基础决策，保证可追溯、可重解析（`pnpm reparse`）、对 AI 生成稳定的契约。

2. **注册表是内容的单一源，不是渲染的单一源**：实施前渲染路径存在三处对注册表的手抄镜像（§2.2）。T7.1 已补齐映射一致性测试并消除属性白名单镜像；类型化属性与行为能力继续按清单推进。

3. **插件化形态**：能力化 + 能力包，四级层级如下。

| 级别 | 名称 | 内容 | 状态 |
| --- | --- | --- | --- |
| L1 | 声明级 | `defineDirective` 注册表，现有 17 个指令 | 已有 |
| L2 | 能力级 | 指令能力三面（interaction / evidence / validation），gen:spec 产出 capabilities.json，教师级辅助能力启用集 | 本阶段核心工作 |
| L3 | 分发级 | 教学包：MD + 能力声明 + 校验器引用，可导入/导出/版本化 | 本阶段后段 |
| L4 | 明确不做 | 运行时加载第三方 React 组件或校验器代码 | 永久拒绝 |

### 1.1 本阶段交付边界（2026-10-09）

- 面向个人项目，先让既有能力声明、渲染、判分、导入导出形成可靠闭环。沿用现有技术栈与服务，不搭通用插件平台。
- 注册表统一能力描述与引用，具体组件、七种题型判分和证据采集仍由现有代码实现。声明本身不会生成新的控件或判分算法。
- 本阶段不增加新题型、部分得分算法、通用证据调度器、自定义 lint 规则语言、能力依赖图或教学包版本管理服务。
- **用户确认（2026-10-09）：能力开关只控制辅助交互，正式作答始终可用。** 不禁用填空、判断、单选、多选和手写题的最终答案输入。
- 教师级设置、现有七种题型路由、教学包当前内容导出是本阶段采用的简单实现边界；课程级覆盖、动态更新、复杂版本关系留到有实际需求时再做。

## 二、现状事实

以下记录实施前的基线事实。T7.1 已为镜像一增加双向一致性测试，将镜像二改为注册表同源推导，并修复原型名称查表；T7.2 已消除组件内属性手工解析（attrs 输出类型由注册表 schema 推导，渲染查表层统一 safeParse）；镜像三（宿主编号特判）Phase 7 不动，落档 `docs/待处理的问题/宿主编号计数器与别名归一待办.md`。

### 2.1 三层架构

- `packages/contract/src/directives.ts`：`defineDirective` 注册表，注册期 fail-fast 校验，是指令"存不存在、叫什么名、有什么属性"的单一权威。
- `apps/web/src/features/markdown/remark/remark-directive-host.ts`：语法树→宿主标签，携带 `directive`（指令名）、`dclass`（样式类）、`index`（展示编号）、`dindex`（文档全局序号）四个语义属性。
- `apps/web/src/features/markdown/directives/index.tsx`：`directiveComponents` 查表映射 React 组件；别名经 `getDirective(name).name` 归一到主名；未知指令渲染 `UnknownDirective` 降级。
- 原文即真相：题目与讲义以 `sourceMd` / `lectures.markdown` 存原始 Markdown，展示时再解析，`pnpm reparse` 可在不改题目 id 的前提下重抽取全部结构化字段；题型与标准答案来自解析结果而非 HTML，步骤结构只用于展示与交互分析。

### 2.2 三处手抄镜像（Phase 7 的消除对象）

**镜像一：指令名 → React 组件（`directiveComponents`）**

- 位置：`apps/web/src/features/markdown/directives/index.tsx`，静态 `Record<string, ComponentType<DirectiveProps>>`。
- 事实：全仓 `listDirectives` 消费方仅 `packages/md-dsl` 的 similarity 与 gen 幂等测试；`apps/web` 未消费，键集合与注册表主名集合之间无任何运行时或测试时的一致性约束。
- 后果：注册表加了条目而组件映射漏加（或反之）时，lint 与构建均通过，运行时静默渲染为 `UnknownDirective`，无测试失败。

**镜像二：属性名 → sanitize 白名单（`DIRECTIVE_HOST_ATTRS`）**

- 位置：`apps/web/src/features/markdown/sanitize.ts`，硬编码 14 个属性名（四个宿主语义属性 + 各指令业务属性）。
- 事实：不引用注册表，不从 `defineDirective` 的 `attrs` 键集合推导。
- 后果：属性名未手动入表时被 `rehypeSanitize` 静默剥除，组件收到 `undefined`，无报错、无测试失败。

**镜像三：宿主编号特判（`remark-directive-host.ts` 计数器）**

- 位置：`annotate()` 内对 `question`/`hint`/`step`/`blank` 与全局 `dindex` 以裸 `node.name` 特判计数；别名归一发生在 L3，晚于 L2 编号生成。
- 后果：评审报告 R06（步骤总数不一致）、R09（别名漏计）源于此。
- **2026-10-08 口径：Phase 7 不动镜像三。** 当前 17 个指令均未声明 `aliases`，R09 属潜伏问题而非现行 bug；待办记于 `docs/待处理的问题/`。

行为轴成本递增的根因即上述镜像：指令的"行为声明"没有统一出口，交互/判分/能力的接入点散落在解析、投影、判分、会话、泄露测试多处（文件清单见 §三）。

## 三、扩展成本基准（现状）

新增一个纯展示指令需要修改：

| 步骤 | 文件 | 动作 |
| --- | --- | --- |
| 1 注册 | `packages/contract/src/directives.ts` | `defineDirective(...)` |
| 2 组件 | `apps/web/src/features/markdown/directives/新组件.tsx` | 实现 `ComponentType<DirectiveProps>` |
| 3 映射 | `apps/web/src/features/markdown/directives/index.tsx` | `directiveComponents` 加一条 |
| 4 样例 | `samples/v2/讲义样例.md` 或新样例文件 | 加示例节点 |
| 5 规范 | `pnpm gen:spec` | 刷新产物，CI 幂等校验 |

T7.1 起，属性穿透 sanitize 由注册表 schema 键集合自动推导，不再手动追加 `DIRECTIVE_HOST_ATTRS`。

新增一个可交互指令额外需要修改：

| 文件 | 动作 |
| --- | --- |
| `packages/md-dsl/src/v2/question.ts` | 解析时识别结构 |
| `packages/md-dsl/src/v2/public-stem.ts` | 投影时剥除或保留内容 |
| `packages/grading/` | 判分逻辑 |
| `apps/web/src/features/markdown/remark/remark-directive-host.ts` | 计数器特判区加入新指令 |
| `apps/server/src/services/attempt-service.ts` 等 | 会话快照处理状态 |
| `apps/server/src/test/assert-no-leak.test.ts` 与相关学生路由测试 | 补泄露测试 |

三档成本：只换题目/材料=零代码；组合已有能力=受约束声明；新增交互能力=按四步注册并适配实际涉及的作答、投影、判分或证据接口。精进后消除手抄白名单、用一致性测试守住遗漏，不承诺全新交互只增加一个校验器即可完成。

## 四、目标架构（能力化）

### 4.1 宿主消费 Zod 属性解析（第一优先）

> **已落地（T7.2，2026-10-09）**：查表层 `withTypedAttrs` 绑定注册表 schema 渲染器表，17 个组件类型化迁移完成；验收见 [实施报告](审查报告/T7.2-实施报告.md)。审查遗留（trim 归一层级、static-markdown 第二通道、失败类别文案、渲染期解析效率）见 `docs/待处理的问题/属性解析归一层级与静态通道待办.md`。

- 现状：宿主标签属性全为字符串，组件在 `DirectiveProps.attrs` 里自行解析类型；注册表 `attrs`（`z.strictObject`）只在 lint 时校验，渲染时不参与。
- 目标：查表后用 `getDirective(name).attrs.safeParse(rawAttrs)` 做一次解析，类型化结果传组件；解析失败降级为 `UnknownDirective`（不抛出）。
- 效果：组件不再自行解析类型；属性合法性在渲染层得到校验；sanitize 白名单可从注册表 `attrs` 键集合自动推导，消除镜像二。
- 本阶段一次性切换全部既有组件，属性输出类型从注册表 schema 推导，不长期保留第二条字符串属性通道。只解析业务属性，`directive/dclass/index/dindex` 不传入 strict schema；样式类沿用现有 `directiveClass` 通道。
- 非法属性沿用上述降级规则，测试必须验证正文保留；正常历史样例保持原语义。主名集合与组件键集合完全相等，别名归一后查主名；查表使用自有属性检查。

### 4.2 指令会话上下文收编

> **已落地（T7.3，2026-10-09）**：`DirectiveSessionContext` 以 fill/telemetry 子命名空间承载两个原 Context，继承/覆盖语义与兼容适配层全部落地；验收见 [实施报告](审查报告/T7.3-实施报告.md)。裸 Context 导出（blankAnswersContext、DirectiveTelemetryContext）随收编移除——唯一消费方已迁移，且形状错配别名本就禁止。

- 现状：填空 Provider 位于题卡外层，遥测 Provider 位于 `RichMarkdown.tsx` 内层，合并时必须保留外层作答状态。
- 目标：统一 `DirectiveSessionContext` 作为所有指令运行时状态的单一出口，两者作为子命名空间合并；新能力（步骤进度、手写草稿引用）在同一 Context 内扩展，不再新增顶层 Provider。
- 实施：保留填空与遥测两个子命名空间，用新 Context 统一承载；内层 Provider 继承外层状态，仅覆盖自身提供的字段。旧 hook、`BlankAnswersProvider` 和原始 context 导出按实际调用点保留适配，不要求不同值形状的 Context 直接互为别名。
- 无作答状态仍返回 `null`，填空显示下划线；无遥测回调静默空操作。折叠和逐步揭晓在教师预览仍可交互，不能因默认空状态而被全局禁用。
- 本任务只收编现有输入与遥测，不预造 `reportEvidence`、提示请求、步骤答案或手写上传接口；后续通过既有服务接入必要字段。

### 4.3 能力三面：interaction / evidence / validation

`defineDirective` 增加可选嵌套字段 `capability`，三面全部可选：

| 面 | 声明内容 | 消费方 |
| --- | --- | --- |
| `interaction` | 输入或操作类型：choice / fill / steps / ink / none | 前端按声明描述既有交互；辅助开关仅消费 steps / ink |
| `evidence` | 现有证据形式：snapshot / ink-strokes / none | 描述现有作答、交互事件或笔迹存储，复用既有采集与冻结链 |
| `validation` | 校验方式：exact / partial / rubric / unverifiable | 服务端判分适配；本阶段 exact 沿用现有比较，rubric / unverifiable 走人工 |

- `unverifiable`：无法自动判定时路由为人工批改（教师端待批队列），不返回错误、不做中间步骤等价判定。
- 未声明 `capability` 的指令行为与现状完全相同。
- 展示和结构类省略 `capability`；只标注已实现的交互或证据。`none` 表示无作答输入，不等于不能点击展开。无判分职责的指令省略 `validation`，不能因省略而创建人工批改项。
- **校验器落地形态（2026-10-08 定）**：纯函数注册表接入 `grade()` 交卷判分链路（查表路由），不新建学生端校验 API；后续若需作答中即时反馈，在注册表之上补端点，不返工。

**既有指令标注表（2026-10-09）：**

| 指令 | interaction.inputType | evidence.format | validation | 说明 |
| --- | --- | --- | --- | --- |
| blank | fill | snapshot | 省略 | 空位输入；具体判分取所在题型，不能把判断题空位也当填空题判分 |
| hint / fold / solution | none | snapshot | 省略 | 展开/收起事件沿用现有遥测；权限和提示获取沿用现有服务 |
| steps | steps | snapshot | 省略 | 逐步揭晓与 reveal 事件，不采集步骤答案、不做部分判分 |
| question / answer / example / step | 省略整个 capability | — | — | 题目结构、标准答案或子级内容；answer 不是学生输入控件 |
| tip / warning / box / columns / col / mark / image / graph | 省略整个 capability | — | — | 展示类指令 |

`snapshot` 是现有作答快照或交互事件的描述，不新增存储格式或冻结策略。注册期只检查 schema 形态与明确的冲突：如 `ink-strokes` 必须对应 `ink`；允许 `none + snapshot` 表达折叠遥测。不为所有组合设计矩阵。`partial` 保留词表，但既有指令不宣称支持部分判分，本阶段也不注册 partial 校验器。

```ts
defineDirective({
  name: "steps",
  // ... 已有字段不变 ...
  capability: {
    interaction: { inputType: "steps" },
    evidence:    { format: "snapshot" },
  },
})
```

**题型与校验器的桥接：** `choice` 是题型，不是已注册指令。为避免猜测指令归属，在 `packages/contract` 建一张小型题型能力表（`questionCapabilityBindings`），以现有 `QuestionType` 为键，声明 inputType、evidence.format、内置 validatorId 和 validation.shape；Zod 定义形态，类型均由契约推导。

| 题型 | inputType | evidence.format | validatorId | validation.shape |
| --- | --- | --- | --- | --- |
| judge / choice / multi | choice | snapshot | 各自题型名 | exact |
| fill | fill | snapshot | fill | rubric |
| solve / apply / find-error | ink | ink-strokes | 各自题型名 | exact |

三个手写题型可以共享同一个实现函数。`exact` 沿用既有归一化与等价比较；无法自动判断仍返回 `null`。服务端 `validator-registry` 按 validatorId 登记函数，`grade(question, answer)` 通过题型表查找；rubric / unverifiable 直接返回 `null`，exact 执行既有函数，外部仍返回 `boolean | null`。不新增得分、reason 载荷或题目级判分策略。测试检查题型表引用均有服务端实现；fill 恒人工、无标准答案优先、客观题未作答判错等现有语义不变。证据字段描述可采集形式，不表示每题必有笔迹；关闭 ink 或未书写时沿用既有缺失证据表达，最终答案照常保存。

### 4.4 capabilities.json 与 gen:spec

- `pnpm gen:spec` 新增输出 `dsl-kit/capabilities.json`，格式对齐 `dsl-kit/schema/content.json` 的风格，供 MCP 工具和 AI 消费。
- **收录范围（2026-10-08 由"仅提取已声明"放宽为全量）**：全量收录全部已注册指令，未声明 `capability` 的条目该字段为 `null`——AI 消费需要完整指令面。
- JSON 形态在 contract 定义：`formatVersion: 1`、`directives`（名称、kind、属性表、capability 或 null）、`questionTypes`（上述题型能力表）。只读取契约元数据，不导入服务端校验器函数；CLI 可据此共享内置校验器名，不引入 grading 的运行依赖。
- MCP 新增 `describe_capabilities` 工具，返回 `capabilities.json` 内容，与现有 `get_dsl_spec` 并列。
- CI 校验：`gen:spec` 后 `git diff` 为空（与现有幂等要求一致）。

### 4.5 能力启用集（profile）

- 定义：本阶段只做教师级辅助能力设置，`enabledCapabilities` 仅允许 `steps` / `ink`，默认两者全启用；空数组合法。choice / fill 是正式作答，none 无需开关，不出现在设置勾选中。
- 目的：让老师选择逐步揭晓和手写辅助方式，正式题目的判断、选择、填空与最终答案输入始终可用。不影响题干投影、判分、既有答案或证据。
- 回退：关闭 steps 时完整展开全部步骤并隐藏「显示下一步」，不伪造 reveal 事件；关闭 ink 时隐藏新增书写/草稿入口，保留最终答案文本输入和已有笔迹的只读查看。不删除既有数据，不增加提交必填规则。
- 实现路径：教师设置保存到教师记录的一个配置字段（drizzle-kit 生成迁移），在学生讲义和作答读取接口下发有效启用集；前端新 Context 与题卡/手写控件共用这一数据。不能只改 Markdown 内部而漏掉 `HandwrittenControls`、`NoteLayer` 等外部入口。教师预览无配置时保持全启用。
- 生效方式：学生重新打开页面或刷新后使用新配置，进行中的页面不做即时同步；读取不到新字段的旧载荷按全启用处理。设置不是证据快照或判分输入，不新增作答配置冻结机制。
- lint：传入启用集时，使用 steps 或手写题型但辅助能力未启用，给 warning 提示实际回退；无上下文时按全启用。正文仍可正常教学，不阻断导入。
- 边界：启用集不是安全边界。答案泄露守卫由 `studentStemMd` 投影和 `assertNoLeak` 测试独立保证，不依赖启用集。

### 4.6 教学包：教学方法即文档

- L3 分发级实体：一份 Markdown 文档（DSL v2）+ 能力声明引用。本阶段不支持自定义 lint 规则集。
- 核心命题：老师的教学方法是可导入、导出、版本化、分享的文档；老师或 AI 用已有 DSL 语法写出新教学方法，不需要写代码，只需选择对应能力面，lint 通过即可导入。
- 边界：教学包不包含可执行代码，只含数据声明和文档内容；运行逻辑全部在系统已注册的能力三面中（这是 L4 不做的直接原因）。
- 导入路径：经既有 `/api/teacher/import/preview` + `/commit` 流程（MCP 侧复用同一管线）；服务端校验能力声明中引用的指令均已注册，未注册能力阻断导入（与 lint 错误机制对齐）。

**最小教学包格式与往返（2026-10-09）：**

- 在既有 frontmatter 增可选命名空间 `teachingPack`：`formatVersion` 缺省 1、`name` 为非空名称、`version` 为非空版本标签（缺省字符串 `"1"`）、`directives` / `validators` 为引用名称数组（缺省空数组）。原有 `kind/dsl/unit/title` 等不变，不新增 document kind。无该字段就是普通 MD。
- 例如已有 practice 文档的 frontmatter 加 `teachingPack: {name: "有理数填空练习", version: "1", directives: [blank], validators: [fill]}`；这是依赖声明，不要求在正文人为增加节点，也不改变 fill 的人工批改规则。
- 指令引用经注册表归一到主名，校验器引用来自题型能力表的 validatorId。只检查显式引用存在；能力面从当前系统清单解析，不复制定义、不覆盖题型路由、不要求文档列齐所有使用的指令。
- 缺失显式引用是 error：`DIRECTIVE_REF_NOT_FOUND` / `VALIDATOR_REF_NOT_FOUND`；普通正文的未知指令仍按既有 warning + 降级。preview、commit、批量导入、ZIP 导入和 MCP 使用同一分析入口，commit 必须重新检查。
- 保存：在 `units` / `lectures` 各增加可空的教学包元数据 JSON 列，形态来自 contract，迁移用 drizzle-kit 生成；同一次导入拆出的资源携带同一声明。正文编辑保留声明，重新导入按新文件声明覆盖（普通 MD 清空旧声明），不建独立包表或历史版本表。
- 导出：在资源库的单元/讲义增加「导出教学包」入口，按当前资源正文导出一个 ZIP，内含 `content.md`（保留 teachingPack）与导出时当前系统生成的 `capabilities-snapshot.json`；正文引用本地图片时复用现有媒体收集与 ZIP 导入方式附带图片，不新增媒体协议。声明过的引用若在当前系统不存在，提示错误而不生成包。
- 同一导入拆出多个资源时，单资源导出只含当前资源，保留同一声明，不重建原混合文档。name/version 是分享标记，导入仍按既有教师域和资源键合并，不新增版本升级算法；用户需要新版本时改标签并重新导入。
- 快照仅供归档和 AI 阅读，不成为运行时权威；已有 ZIP 导入取 `content.md` 复用同一管线，忽略附带能力快照。以「导入 → 导出 → 再导入」验证正文语义与声明保留，不要求排版逐字节一致。

## 五、插件化边界（L1–L4）

- **L1 声明级（已有，维持）**：`defineDirective` 注册表是内容的单一源。维持 fail-fast 校验与"注册表→组件→样例→gen:spec"四步纪律，不绕过注册表。
- **L2 能力级（本阶段做）**：注册表和契约题型表统一能力元数据；组件、判分与证据实现复用现有代码，通过测试约束声明与实现一致。三面全部可选；不预造通用行为执行器。
- **L3 分发级（本阶段后段）**：教学包的导入/导出/版本化，导入端校验引用完整性（缺失依赖是 error，不是 warning）。
- **L4 明确不做（永久拒绝）**：运行时加载第三方 React 组件或 JavaScript 校验器代码。理由：①与"无 CDN、自部署零第三方依赖"硬规则正面冲突；②绕过 `rehypeSanitize` 白名单机制；③第三方组件可在渲染时读取学生上下文并外泄，违反学生端零泄露约束；④引入契约版本矩阵（系统版本 × 插件版本）风险，维护成本极高；⑤单人 + AI 开发、无社区生态，收益为零。
- **"老师选能力"的落点**：L2 能力启用集（教师端配置界面或 MCP），是数据层配置，不是代码层加载。

## 六、必须保持的不变量

任何精进步骤不得违反：

1. **契约单一源**：任何数据结构改动先改 `packages/contract` 的 Zod schema，再改实现。禁止在前后端各自手写同一个类型。

2. **投影不变式**：学生可见的题干必须来自 `packages/md-dsl/src/v2/public-stem.ts` 的 `studentStemMd`，不得把教师域 `sourceMd` 直接暴露给学生端渲染器。

3. **判分只在服务端**：`packages/grading` 是唯一合法的判分执行位置。客户端计算的判分结果不可信，不得进入数据库。

4. **清洗白名单必须与注册表同源**：T7.1 已将 `sanitize.ts` 的属性白名单改为从注册表 `attrs` 键集合自动推导；不得恢复手抄。只对指令宿主放行，沿用既有 id/class 处理与危险协议拦截。

5. **组件不决定权限**：React 组件不得自行判断"当前用户是否有权看到答案"。权限判断在服务端载荷投影阶段完成，组件只渲染收到的内容。

6. **注册表主名集合与组件映射集合一致**：`listDirectives().map(d => d.name)` 的集合与 `Object.keys(directiveComponents)` 的集合必须完全相同。T7.1 已用测试强制检查缺失与多余映射；组件表仍显式维护。

7. **未知指令优雅降级**：任何在注册表中不存在的指令名，渲染结果必须是 `UnknownDirective`（保留正文，不抛错，不崩溃）。`directiveComponents` 的查表必须用自有属性检查（`Map` 或 `Object.hasOwn`），不得利用原型链（R04 根因）。

8. **已有样例语义不变**：`samples/v2` 下的所有样例文件是兼容性回归测试基准。任何解析器或渲染器改动后，这些样例必须仍能解析且渲染一致。

9. **新属性可选且有默认值**：`defineDirective` 中新增的 `attrs` 字段必须可选（`.optional()` 或 `.default(...)`），禁止新增必填属性，否则会破坏历史已导入文档的解析。

10. **证据不可变**：Phase 6 已实施的版本冻结链（`note-store.ts` 的 CAS 机制）不得被绕过或简化。教学包引用的已冻结证据不可被修改，只能被新版本追加。

## 七、测试与质量闸门增量

只增量添加，不引入新依赖：

**7.1 注册表↔组件映射一致性测试**（清单 T7.1 落地，文件 `apps/web/src/features/markdown/directive-registry-consistency.test.ts`）

- 正向断言：注册表主名集合与 `directiveComponents` 自有键集合完全相等，同时检测漏项和多余项。
- 反向断言（关键）：fixture 内删掉或多加一条映射，一致性校验必须失败；最终测试用例自身应通过。
- 别名断言：`getDirective(alias).name` 归一后的主名在 `directiveComponents` 中存在。

**7.2 清洗白名单↔注册表一致性测试**

- T7.1 已落地：断言推导结果 == 注册表 `attrs` 键集合并集 ∪ 四个宿主语义属性，并检查三种宿主实际使用该白名单。
- fixture 增删 schema 属性验证推导结果随来源变化；当前注册定义均为 ZodObject，若将来改变 schema 形态，必须同步调整推导与测试。

**7.3 样例自动发现**（清单 T7.9 已落地，辅助 `test-support/dsl-samples.ts`）

测试动态读取 `samples/v2/` 所有 `.md`：每份文档进入解析回归，讲义进入目录/编号一致性测试，练习题进入题面渲染测试，不能只遍历 `parsed.lectures` 而漏掉纯练习文件。渲染复用当前学生投影与控件，验证必要语义，不创建大规模 HTML 快照。

`完整样例.md` 只解析其中实际 Markdown 样例块，从 AST 收集精确指令名（语法糖经过现有 blank 转换）；不能用主名子串搜索代替覆盖断言。

**7.4 能力清单幂等**

`capabilities.json` 并入 CI 既有幂等检查：`gen:spec` → `git diff` 为空。快照变化视为有意改动，必须显式提交。

**7.5 一致性测试的反证**

一致性测试文件内置“删除/多加映射、从推导来源移除属性键”的 fixture：前者验证一致性校验能报错，后者验证推导结果随来源变化；最终测试本身通过。无需另建 CI 变异测试框架。

**风险一：清洗白名单不同源导致的静默丢属性（T7.1 已消除手抄来源；T7.2 已收敛组件侧解析与重复默认值）**

**风险二：能力清单与实现漂移**
`capabilities.json` 是声明，判分/交互实现在代码中。本阶段只标注已经实现的行为；题型表与服务端注册表之间做引用完整性测试，判分保持既有等价性测试。折叠/揭晓验交互事件，作答验交卷结果；不强迫无判分职责的指令进入判分链路。partial 不列为已实现能力。

**风险三：启用集引入的学生端降级歧义**
用户已选择正式作答始终可用：启用集仅包含 steps / ink，回退分别为全部步骤展开和保留文本答案。测试关闭全部辅助能力后仍可作答、提交、判分，已有答案/证据不丢失。不设计「不可作答但照常判错」的状态。

**风险四：教学包引用校验不足**
教学包导入时若被引用的能力在当前系统版本中未注册，阻断导入并给出明确错误，不能静默接受。与 DSL 兼容规则（未知指令 warning + 降级）的处理策略不同——教学包是明确声明了依赖的，缺失依赖是错误，不是警告。
