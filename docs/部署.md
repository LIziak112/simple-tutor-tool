# 部署文档

> 适用：simple-tutor-tool v2（T0.7 产出）。架构与决策背景见 `docs/技术架构与实施方案.md`（下称"架构文档"）§2.4（部署选型）、§5.10（部署、备份与运维——HTTPS/备案决策）。
>
> 部署形态：**单进程、自部署、数据自持**——一个 Node 进程 = API + 静态页面；数据 = `data/tutor.db`（SQLite WAL）+ `data/blobs/` + `data/shared/`（共享发布）+ `data/backups/`，全部在 `DATA_DIR` 下。多教师、注册开关与共享目录的日常使用见本文 §3；从旧版切换到 v2 见 §5。

---

## 0. 两种部署方式与目录说明

| 方式 | 适合 | 入口 |
| --- | --- | --- |
| Docker Compose（推荐） | 服务器有 Docker；一条命令起 app + Caddy，升级就是重新 build | 本文 §1 |
| systemd（非 Docker） | 沿用现有 ECS 上裸 Node 的习惯（架构文档 §2.4 保留项） | 本文 §2 |

**与架构文档 §4 目录图的差异说明**：§4 把 `Dockerfile`、`compose.yaml`、`Caddyfile` 都画在 `docker/` 下，实际布局是——

```
simple-tutor-tool/          ← 检出根
  Dockerfile                ← 在仓库根（不在 docker/）
  compose.yaml              ← 在仓库根（不在 docker/）
  .dockerignore             ← 在仓库根（Docker 固定读取"构建上下文根"下的 .dockerignore）
  docker/
    Caddyfile               ← 保留在 docker/，由 compose 只读挂载进 caddy 容器
```

原因：`compose.yaml` 里 `app` 服务是 `build: .`，构建上下文必须是**整个 pnpm workspace**（构建过程要在容器内 `pnpm install` 并编译 `apps/server`、`apps/web`，三者与 `packages/*` 相互依赖），且验收命令 `docker compose up -d --build` 要求在检出根目录直接可用；`Caddyfile` 不参与镜像构建，只是挂载文件，放 `docker/` 更整洁。

## 1. 方式一：Docker Compose（推荐）

### 1.1 前置条件

- 服务器已安装 Docker Engine 与 Compose v2 插件：`docker compose version` 能出版本号。
- 检出仓库（要部署的分支/tag），`cd` 到检出根。
- 安全组 / 防火墙放行 80（HTTP 模式）或 80 + 443（HTTPS 模式）。

### 1.2 首次启动

```bash
# 容器内以非 root 的 node 用户（uid/gid 1000）运行，bind 挂载的宿主目录必须可写。
# 若跳过这步，Docker 会自动创建 root 属主的 data/，容器内写入会报 EACCES（见 §4.1）。
mkdir -p data && sudo chown -R 1000:1000 data

docker compose up -d --build     # 构建镜像并启动 app + caddy
docker compose ps                # app 一列显示 (healthy) 即健康检查通过
curl http://localhost/api/public/health
# → {"ok":true,"data":{"time":"…UTC ISO…"}}
```

浏览器打开 `http://localhost`（云服务器上用 `http://公网IP`），首页应显示服务器时间。

首次启动时应用自动：建 `data/` 目录与会话密钥 `secret.key` → 创建 `data/tutor.db` 并执行迁移 → 进入教师端设置向导（设置**登录名 + 密码**——首位教师即管理员，见 §3）。

### 1.3 验收自检（对应开发任务清单 T0.7，🧑 待人工验证）

> 开发机（Windows）无 Docker，以下两条验收需在服务器上人工执行：

1. **🧑 `docker compose up -d -‑build` 后 `http://localhost` 可访问首页**——按 §1.2 操作，浏览器打开 `http://localhost` 看到首页（显示服务器时间）即通过。
2. **🧑 重建容器后 `data/` 数据仍在**——使用系统产生一些数据（如完成教师设置向导）后执行：

   ```bash
   ls data/                # 宿主机上可见 tutor.db、secret.key 等
   docker compose down     # 只停删容器，不动 ./data 与命名卷
   docker compose up -d --build
   ```

   刷新页面：教师密码仍然有效、数据仍在，即通过（数据在宿主机 `./data`，与容器生命周期解耦）。

健康检查明细：`docker compose ps` 的 STATUS 列出现 `(healthy)`；也可手动验证：
`docker compose exec app node -e "fetch('http://127.0.0.1:8787/api/public/health').then(r=>r.json()).then(console.log)"`。

### 1.4 数据目录与备份

宿主机 `./data`（容器内 `/app/data`）：

| 内容 | 说明 |
| --- | --- |
| `tutor.db` | SQLite 主库（WAL 模式，运行时另有 `tutor.db-wal` / `tutor.db-shm`） |
| `blobs/` | 手写笔迹与快照文件 |
| `shared/` | 共享发布目录（Phase 2B）：在线发布的快照与手动放入的 `.md`（用途见 §3.3） |
| `backups/` | 应用内每日 `VACUUM INTO` 自动快照（T4.4 实现） |
| `secret.key` | 会话密钥（首次启动自动生成）。**务必随数据一起备份**，丢失则已签发的会话全部失效 |

- **备份 = 备份整个 `data/` 目录**（或先用教师端"下载完整备份 zip"）。注意 `tutor.db` 是 WAL 模式，**运行中直接拷贝可能拿到不一致快照**：优先用应用内备份；或 `docker compose stop app` 停服后再拷。
- **恢复**：`docker compose stop app` → 用备份覆盖 `data/`（注意保持属主 1000:1000）→ `docker compose start app`。
- `docker compose down -v` 会删除 `caddy_data` / `caddy_config` 命名卷（只丢 Caddy 证书缓存，业务数据不受影响）；**不要**对 `./data` 所在目录做删除操作。

### 1.5 升级

```bash
git pull
docker compose up -d --build   # 重新构建镜像并替换容器；数据在宿主机 ./data，不受影响
docker compose logs -f app     # 观察启动与迁移日志（迁移幂等，可重复执行）
```

回滚：`git checkout <上一个可用 tag/commit>` 后同样执行 `docker compose up -d --build`（涉及数据库结构变更的回滚需先咨询迁移记录，禁止手改线上库）。

**从 Phase 2A 及更早版本升级到多教师版（Phase 2B）**：升级即完成——启动时迁移自动加列/重建表并回填，**原教师自动成为管理员**（登录名置为 `teacher`，密码不变）：升级后用 `teacher` + 原密码登录即可，顶栏显示 `teacher`，侧边栏多出「管理」入口（教师账号、注册开关、共享文件，见 §3）。全部业务数据（资源库、课程、学生、作答）原样保留、自动归属该教师。

### 1.6 切换 HTTPS（域名，备案完成后）

决策背景与备案流程见架构文档 §5.10（已决定办理备案；完成前用 `http://公网IP` 使用，功能完整，仅无 PWA）。

1. 域名解析到服务器，80/443 在安全组放行；
2. 编辑 `docker/Caddyfile`：注释掉整个 `:80` 块，解开域名块并改成真实域名；
3. 编辑 `compose.yaml`：`app` 服务的 `PUBLIC_URL` 改为 `https://你的域名`；
4. `docker compose up -d` 重建。Caddy 自动向 Let's Encrypt 申请并续期证书（证书在 `caddy_data` 卷）。

HTTPS 生效后服务端自动开启 Secure Cookie 与 Service Worker（PWA 可安装、可离线缓存），无需改代码。

PWA（T2.12）的开关机制：前端入口启动时请求公开接口 `GET /api/public/config`，
`pwaEnabled` 为 true（即 `PUBLIC_URL` 以 `https://` 开头）才注册 Service Worker；
纯 HTTP 环境不注册、全部功能照常。SW 只预缓存静态资源（JS/CSS/字体/图标，
约 10.6MB；Excalidraw 字体约 14MB 不进预缓存，改为首次使用后按需缓存），
绝不缓存任何 `/api/*` 请求——离线时作答与草稿走本地 IndexedDB（T2.9），
交卷按钮在离线时禁用并提示「恢复网络后可交卷」。
应用图标目前为占位自绘图（`apps/web/scripts/generate-icons.mjs` 生成），
正式图标确定后替换 `apps/web/public/icons/` 并重新构建即可。

## 2. 方式二：systemd（非 Docker）

以部署目录 `/srv/simple-tutor-tool` 为例，Linux 服务器上执行。

### 2.1 构建产物

```bash
# 需要 Node.js 24（与 .nvmrc / engines 一致）与 pnpm 12.6.0
corepack enable                    # 或：npm install -g pnpm@12.6.0
cd /srv/simple-tutor-tool
pnpm install --frozen-lockfile
pnpm --filter server build && pnpm --filter web build
# 产物：apps/server/dist（index.js + migrations/）与 apps/web/dist
# 两者的平级关系不能变：server 运行时按自身位置上溯两级找 ../web/dist
```

### 2.2 运行账号与数据目录

```bash
sudo useradd -r -s /usr/sbin/nologin tutor 2>/dev/null || true
sudo mkdir -p /srv/simple-tutor-tool/data
sudo chown -R tutor:tutor /srv/simple-tutor-tool/data
```

### 2.3 systemd unit

写入 `/etc/systemd/system/simple-tutor-tool.service`：

```ini
[Unit]
Description=simple-tutor-tool (Node 单进程: API + 静态页面 + SQLite)
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=tutor
Group=tutor
# cwd 在 apps/server，与 CMD node dist/index.js 对应；
# DATA_DIR 用绝对路径显式指定，不依赖 cwd 解析默认值 ./data
WorkingDirectory=/srv/simple-tutor-tool/apps/server
ExecStart=/usr/bin/node dist/index.js
Environment=NODE_ENV=production
Environment=PORT=8787
Environment=DATA_DIR=/srv/simple-tutor-tool/data
# 无反代直连时写 http://服务器IP:8787；前面另架了 Caddy/Nginx 做 HTTPS 则写 https://你的域名
Environment=PUBLIC_URL=http://服务器IP:8787
Restart=always
RestartSec=3
# 轻量加固（可选）
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ReadWritePaths=/srv/simple-tutor-tool/data

[Install]
WantedBy=multi-user.target
```

启用与验证：

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now simple-tutor-tool
systemctl status simple-tutor-tool
curl http://127.0.0.1:8787/api/public/health   # {"ok":true,...} 即正常
journalctl -u simple-tutor-tool -f             # 看日志
```

说明：

- 静态页面由 `dist/index.js` 自动定位 `../web/dist` 托管（含 SPA 回退），无需额外配置；
- 数据与备份同 §1.4（`DATA_DIR` 即数据目录）；备份时同样建议先 `systemctl stop simple-tutor-tool`；
- 此方式下 8787 直接对客户端（安全组放行 8787）；如需 HTTPS，可再架一层 Caddy（`Caddyfile` 写法同 `docker/Caddyfile`，`reverse_proxy` 目标改为 `127.0.0.1:8787`）；
- 升级：重新执行 §2.1 构建，然后 `sudo systemctl restart simple-tutor-tool`。

## 3. 多教师、注册开关与共享目录（Phase 2B 起）

### 3.1 多教师与管理员

系统支持多位教师，各自拥有**完全隔离**的资源库、课程、作业与学生（互相看不见，按 id 访问他人资源返回 404）。首位教师即管理员；管理员可兼任全部教学功能，另可通过侧边栏「管理」入口进入管理端 `/a`：管理教师账号（创建 / 改登录名 / 重置密码 / 禁用启用 / 授予撤销管理员）、注册开关、共享文件。管理员看不到任何教师的业务数据（题库、课程、学生、作答）。

从旧版升级的说明见 §1.5（原教师自动成为管理员，`teacher` + 原密码登录）。

### 3.2 注册开关（默认开，公网部署建议关闭）

教师自助注册入口（登录页底部「没有账号？注册」）由**注册开关**控制，**默认开启**：

- 开关位置：管理端 `/a` 概览页的「允许教师自助注册」行，就地切换（也可让管理员直接创建账号，不受开关影响）。
- 关闭后：注册接口返回 403，登录页/注册页显示「注册已关闭，请联系管理员」。
- **公网部署建议关闭**：注册是匿名可达的公开接口（虽有按 IP 限流——同一 IP 1 小时最多 5 次），公网环境下开着意味着任何访客都能自建教师账号。局域网/家庭使用可保持默认开启。
- 开关状态存于数据库 `app_settings` 表（`allowRegistration` 键），重启不丢。

### 3.3 共享目录 `data/shared/`

教师间共享内容的统一落点。两条进入路径，同源并列：

1. **在线发布**：教师在资源库的单元/讲义详情点「发布到共享」，系统把当前内容写成独立快照 `.md`（文件名 `标题-发布者-时间戳.md`）放入该目录——发布后源内容继续修改**不影响**已发布文件；伴生 `.meta.json` 记录发布者与时间。
2. **本地放入**：直接把 `.md` 文件放进服务器的 `data/shared/` 目录（U 盘拷贝、网盘同步、`scp` 上传皆可，无需重启）——共享页（教师端侧边栏「共享」）即时列出，来源标签显示「本地文件」，**仅管理员可删除**。

任何教师可在共享页浏览、预览并「导入到我的资源库」（导入进**自己的**域，与发布者无后续关联）。文件须符合 DSL 导入格式；目录只列出前 200 个文件、单文件超过 1 MB 不列出。教师只能删除自己发布的文件；删除不影响已导入的内容。

### 3.4 多教师备份提示

**备份整个 `data/` 目录即覆盖多教师全部数据**——数据库（全部教师与学生）+ 笔迹文件 + 共享目录 + 会话密钥都在其中，操作见 §1.4（SQLite WAL 模式，优先应用内备份或停服后拷贝）。

## 4. 常见问题

### 4.1 容器启动失败 / 健康检查不通过

排查顺序：

1. `docker compose logs app`、`docker compose ps` 看状态与日志；
2. **权限**：日志出现 `EACCES` 多半是 `data/` 属主不是 1000:1000 → `sudo chown -R 1000:1000 data`；
3. **端口**：80/443 被占用 → 改 compose 的 ports 映射或停掉占用进程；
4. **首启慢**：首次建库迁移超过 20s（start-period）会多等一轮健康检查，属正常；持续 unhealthy 才是异常；
5. 手动验证服务本身：`docker compose exec app node -e "fetch('http://127.0.0.1:8787/api/public/health').then(r=>r.json()).then(console.log)"`。

### 4.2 数据备份与恢复

见 §1.4。要点：备份整个 `data/`（含 `secret.key`）；SQLite 是 WAL 模式，运行中拷贝主库文件有拿到不一致快照的风险，优先应用内备份或停服后拷贝。

### 4.3 HTTP → HTTPS 切换

见 §1.6（Docker 方式）。systemd 方式同理：改反代 Caddyfile + `PUBLIC_URL` 环境变量后重启服务。备案决策与流程见架构文档 §5.10。

### 4.4 为什么不要把基础镜像换成 alpine

`better-sqlite3` 的原生绑定是按平台分发的预编译二进制，glibc（Debian 系 `node:24-slim`）与 musl（alpine）ABI 不通用；换 alpine 会导致原生模块加载失败或需要额外工具链自行编译。当前 `node:24-slim` + 包内 `linux-x64` 预编译开箱即用，无需任何编译工具链。

### 4.5 镜像里有哪些东西

最终镜像只包含：server 构建产物（`dist/index.js` + `dist/migrations/`）、web 静态产物（`apps/web/dist`）、server 生产依赖（hono / @hono/node-server / pino / better-sqlite3 及其传递依赖，其余代码已打进 bundle）。不含 devDependencies、不含构建工具链、不含源码与文档。

## 5. 上线切换（从旧版切到 v2，Phase 3 收尾定稿）

> **无数据迁移步骤**（用户决策 D14，2026-09-29，架构文档 §10 第 9 条）：旧版的 `content.json`、`submissions` 与 base64 手写图等历史数据**不迁移**——内容以 .md 重新导入，作答历史从 v2 重新开始积累。原「migrate-v1 迁移脚本」方案已整体取消。

1. **全新部署**：按 §1（Docker Compose，推荐）或 §2（systemd）在目标服务器上部署 v2；首次启动走完设置向导（登录名 + 密码，首位教师即管理员）。公网部署建议先关闭教师自助注册（§3.2）。
2. **内容重新导入**：把旧版的练习/讲义整理成 `.md` 文件（**v1、v2 DSL 均可**——v1 格式解析器仍内置，导入时自动识别），经教师端「资源库 → 导入内容」进入新资源库；多文件/选文件夹批量导入、逐文件预览与冲突检测均可用（T2A.3）。旧版的 .md 原文可直接使用，无需改写。
3. **学生重新建档**：在 `/t/students` 重建学生名单（姓名 + 登录名 + 专属链接/密码），把新的专属链接发给学生即可开始使用；旧版作答历史不搬（如需留档，旧版数据文件整体归档留存备查）。
4. **旧版下线**：新系统冒烟无误后（建议按 Phase 3 完成标志走一遍：部署 → 导入样例 .md → 教师批改 / 学生记录全流程），旧服务可直接停掉。
5. 部署演练即 Phase 3 的完成验收项（`docs/Phase3任务清单.md` T3.6）：本机 Docker 或服务器均可。
