# 标画底图公式缺失：验证与修复方案

验证日期：2026-10-14。范围：当前工作区代码、实际安装的 html-to-image 1.11.13、Chromium（系统 Edge）与 Playwright WebKit。前文记录实施前的验证与方案；实施结果见文末。

## 结论

原分析指出的字体缓存问题成立，字体请求失败被转换为空源的问题也成立。但现有证据不足以认定指定作答第 16 题的公式整行消失由 Safari 字体时序造成，也不足以把“预热一次、等待 50ms”作为可靠修复。

本轮没有取得用户原始两张截图、该作答的实际底图、生成时网络记录或 iPad Safari 环境；未访问线上作答数据。以下实验验证机制与代码风险，不等于已复现该作答的原始故障。

## 修复前已确认的代码问题

1. `apps/web/src/features/notes/rasterize-utils.ts:125` 使用宿主节点作为 WeakMap 缓存键，永久保留成功返回的字体 CSS。应用样式资源可以不变，但节点实际使用的字体集合会变。
2. `apps/web/src/features/annotation/question-base-image.tsx:265` 始终使用 `document.body` 收集字体。库的 `getUsedFonts` 遍历当时的元素树，并按计算字体家族筛选字体规则。因此首次没有某字体时，缓存不会随新题挂载而补齐。此管线首次收集时导出副本已挂载，所以“第一次就遗漏当前公式”并非必然，关键是此前是否已有缓存。
3. 库的 `embedWebFonts` 以 `fontEmbedCSS != null` 判断是否采用传入配置；空字符串也会跳过自动收集。上游说明与本地源码一致：[html-to-image 官方说明](https://github.com/bubkoo/html-to-image#fontembedcss)。
4. 库的 `resourceToDataURL` 捕获资源请求失败后返回空字符串，并将其写入自己的模块缓存；`embedResources` 将源 URL 替换为空源。外层 Promise 并未拒绝，项目的“失败不缓存”逻辑不会执行。仅重新调用 `getFontEmbedCSS` 也可能再次拿到库缓存的失败结果。
5. 相同的 body 缓存还用于 `annotation/base-image.ts` 与 `notes/export-review-image.ts`。这两条管线在离屏内容挂载前收集字体，风险不只限于新题面底图。
6. `samplePngBlank` 检查整页空白。即使公式完全缺失，只要中文、边框或输入框仍有像素，就可能通过检查。
7. `question-annotation-base.ts:45` 优先返回本机已缓存底图，之后也会复用服务端 ready 底图。修好生成函数不会自动修复已保存的残缺 PNG。

## 对原分析的修正

- DOM → SVG foreignObject → Image → Canvas → PNG 的描述成立。
- KaTeX 使用专用字体的判断成立，但“字体缺失必定使所有公式字符透明”未获验证；本轮缺少嵌入字体时仍绘出了公式区域的部分像素，可能发生字体回退或字形变化。
- 空源会使指定字体资源失效，但不能由此推断它必定阻断所有字体回退。
- `document.fonts.ready` 已在新题面生成管线中等待，不能将新增同一句等待当作修复。
- 当前库的 `createImage` 已等待 SVG 图片的 `onload`、`decode()` 和下一次动画帧。它不保证所有 Safari 版本完全可靠，但说明“尚未等待图片解码”并非现状。
- 未证明部署中的字体相对路径确实错误。Vite 会处理导入 CSS 中的字体资源，必须依据实际产物、请求 URL 与响应验证，不能因源码出现相对路径便认定部署失败。
- 上游有 iOS 图像遗漏报告，但不等于本例 KaTeX 字体原因已确诊：[上游问题记录](https://github.com/bubkoo/html-to-image/issues/420)。固定延时与吞掉首轮异常只能作为待验证的兼容手段。

## 实验结果

### 字体集合变化实验

使用项目实际 KaTeX CSS、字体文件和 html-to-image，在独立浏览器页面中先收集无公式 body，再挂载原分析中的极限公式。为隔离请求路径与失败因素，字体文件以 data URL 嵌入 CSS。

统计公式容器中的深色像素，仅用于检测完全空白及比较输出，不证明每个字形都正确。

| 浏览器 | 先收集的 CSS 长度 | 当前节点 CSS 长度 | 旧 CSS 输出像素 | 当前 CSS 第一次输出像素 | 当前 CSS 第二次输出像素 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Chromium | 0 | 653989 | 790 | 958 | 958 |
| WebKit | 0 | 653989 | 742 | 767 | 767 |

当前节点 CSS 包含 `KaTeX_Main`、`KaTeX_Math`。确认旧快照不能覆盖后来出现的字体，但没有复现整行透明。这里完整字体的第一次输出发生在旧 CSS 输出之后，不能作为独立冷启动首轮成功的证明。

### 当前应用管线实验

启动独立 Vite 于 5199，使用现有 `/dev/question-base` 夹具，在同页依次生成 judge、fill。API 请求在浏览器中以空对象隔离，未连接作答数据库；本实验不验证登录、接口或线上题目。

```text
Chromium judge: generated=true
Chromium fill: generated=true, mathDarkPixels=555, cachedCssLength=103477
WebKit judge: generated=true
WebKit fill: generated=true, mathDarkPixels=550, cachedCssLength=103467
```

两个浏览器均生成底图，公式区域非完全空白。这是现有分数公式夹具的结果，不是原第 16 题的现场复现。实验后停止独立 Vite。

### 字体请求失败与恢复实验

使用真实 `KaTeX_Main-Regular.woff2`：先让页面字体加载成功，再让嵌入请求返回 404，之后恢复请求并重新收集字体。

```text
failureReturnedEmptySrc=true
retryStillEmpty=true
requestsDuringRetry=0
```

确认库内部失败缓存会让后续收集继续返回空源；移除项目 WeakMap 不能单独解决此问题。

## 建议实施计划

### 第一步：先补失败测试

- 新增 `apps/web/src/features/notes/rasterize-utils.test.ts`：同一节点先无公式后有公式；同家族不同字重与样式；并发请求；失败后资源恢复必须真实重试；空源、非字体响应和超时不得被当作成功。
- 扩充 `question-base-image.test.tsx`：以当前导出副本收集字体、字体失败拒绝生成、离屏宿主必定清理，并保留公开题面守卫。
- 扩充 `QuestionBaseDevPage.tsx` 与 `e2e/question-base.spec.ts`：加入原极限公式，覆盖冷启动首轮、先普通题后公式题、不同字体家族、连续生成、字体请求失败再恢复。
- 浏览器测试检查每个公式区域的 PNG 像素及字形/布局对照；不能只断言存在 PNG、文件非空或整页非白。继续覆盖中文、填空框、分式与上标。

### 第二步：修复共享字体处理

- 每次根据已挂载且资源稳定的实际导出节点计算所需字体集合，不缓存可变 body 的最终 CSS 快照。
- 成功的字体资源可按规范化绝对 URL 缓存；字体规则保留 family、weight、style 等描述符。并发资源请求可以共享，失败必须移出缓存。
- 对应用本地字体使用严格的资源读取与 data URL 嵌入，检查响应状态和字体数据；不依赖 html-to-image 吞掉错误并缓存空字符串的资源分支。向栅格化调用传入已验证的自包含字体 CSS。
- 相对 URL 按样式表 URL 解析；内联样式的资源按正确文档基址处理。只采用项目本地资源，不新增 CDN 或依赖。
- 不使用 `catch(() => {})` 隐藏字体失败。字体缺失明确提示“公式字体加载失败，请重试”，不得保存残缺底图。
- 新题面、旧底图与回看导出统一采用修复后的工具。后两条管线将收集时点移到离屏内容挂载后，并针对整份实际导出内容收集字体，供分页复用。

涉及实现文件：`notes/rasterize-utils.ts`、`annotation/question-base-image.tsx`、`annotation/base-image.ts`、`notes/export-review-image.ts`；对应单测与上述夹具、E2E 同步更新。

### 第三步：针对 WebKit 验证兼容措施

- 首先验证正确嵌入字体后的冷启动输出。
- 如果仍能稳定复现首轮缺失、第二轮恢复，再添加有超时、可观测失败的有限重试或预解码措施；所有轮次使用同一固定公开题面与尺寸。
- 不把固定等待 50ms 当作正确性保证。浏览器测试外仍需实际 iPad Safari 验证，尤其检查公式字形、上标、分式与笔迹位置。
- 可增加完全空白公式区域的产物守卫；该守卫只能识别完全缺失，不能保证公式符号完整，也不能代替图像对照回归。

### 第四步：已有残缺底图的恢复

- 单独读取原问题底图与布局，确认 PNG 本身是否缺公式，还是展示/叠加层问题。
- 未有笔迹、未绑定服务端且未封存的本机底图，可以在明确的安全条件下重新生成。
- 已有笔迹、服务端绑定或封存的底图保留原稿，不自动清库或覆盖。修复背景必须先确认题目版本、底图 CSS 尺寸和笔迹坐标一致，并使用现有服务端约束允许的恢复流程；不满足条件时保留查看原标画入口。
- 不直接修改 `renderVersion` 或布局签名来批量失效旧数据。当前契约使用固定版本 literal，改变版本还需要契约兼容与历史数据迁移设计。若最终新增恢复接口，先改 contract，再实现并补学生端泄露测试。

### 第五步：质量闸门与验收

计划确认后在独立分支 TDD 实施。完整 diff 依次做 simplify、code-review；涉及学生端载荷/答案边界时加 security-review。运行相关单测、`pnpm typecheck`、`pnpm lint`、`pnpm build`，以及隔离环境的 Chromium/WebKit E2E，记录真实输出。现存 samples 保持兼容；契约变更时执行 schema/spec 生成。完成真机手动验证说明后，按项目规则合并 v2，再发 main。

以上为方案阶段的验证，不将这些实验称为修复验收通过。

## 实施记录

修复分支：`codex/annotation-font-embedding`，从 `v2` 的 `5d9a983` 创建，目标为合并 `v2`。

### 最终行为

- 新题面底图、旧底图、回看分页合成图使用同一字体工具，从已挂载的实际导出副本收集所需字体，不复用 body 的字体快照。
- 字体请求绕过 html-to-image 的失败资源缓存。使用本站资源或内嵌资源，按样式表地址解析相对 URL，优先 woff2，保留字重、样式、unicode-range 等描述符。
- HTTP 错误、空源、HTML 假成功响应、字体解码失败或超时均明确拒绝导出；进行中的同 URL 请求共享，成功资源复用，失败移出缓存，下一次真实重试。
- 未加入无依据的固定延时或双次截图。保留公开题目重建、答案标记守卫、原尺寸与签名机制；未修改学生 API、契约、数据库或历史笔迹。
- 已有残缺底图的恢复需要针对实际稿件另行确认几何与绑定状态，本次不覆盖已有缓存、服务端绑定或封存底图。

### TDD 与质量闸门

先补字体集合变更、失败重试与离屏收集时点测试：首次运行 7 项失败、10 项通过。修复后通过。审查发现仅看文件头不足以排除损坏字体，又先补原生解码失败测试，确认失败后加入 `FontFace.load()` 校验。

仓库所引用的 systematic-debugging、simplify、code-review、security-review、verification-before-completion 技能文件在本会话技能列表与本地技能目录均未找到；因此按仓库明确描述的纪律完成同等检查，未宣称调用了这些缺失技能。

完整 diff 先做复用/简化检查，再做正确性与安全边界检查：

1. 三处调用复用一个工具；移除旧管线重复的字体等待与吞异常分支，避免额外预热或复杂缓存失效层。
2. 修复审查发现的字体解码校验遗漏及 TypeScript 严格索引类型问题，更新依赖注入注释和管线步骤顺序。
3. 检查超时和失败缓存的清理、并发共享、相对路径、字体描述符、离屏宿主释放及页级复用。
4. 核查学生底图仍只从公开题目重建，字体工具不获取正文/答案数据；未添加接口，未改变答案投影、判分或封存行为。原公开题面拒绝测试及原位标画、账号隔离 E2E 保留。

### 手动验证说明（供变更审阅使用）

1. 开发环境访问 `/dev/question-base`，宽度设为 720；先选 judge 生成，再依次选 limit、mathFonts 生成。对照正常题面与 PNG，检查极限、无穷符号、斜体、上标、分式、根号、积分及填空框，重复生成结果应稳定。
2. 在开发者工具中阻断 KaTeX woff2 的嵌入请求：生成应报告字体错误且不出现 PNG；解除阻断后在同页重试，应恢复生成。
3. 用实际 iPad Safari 打开一份尚无标画底图的公式题，创建标画并导出，检查公式字形、笔迹位置与题面坐标一致；再验证普通题切换到公式题。
4. 打开已有标画与结果回看，确认原稿仍可查看、笔迹未被替换。原先已损坏的保存底图不会因本修复自动变为新底图。

实际 iPad Safari 未在本环境连接，真机表现仍需按上述说明试写确认。浏览器像素测试按公式左、中、右三区与正常 DOM 截图比较，防止完全缺失或显著字形偏差；它不宣称逐像素一致或覆盖所有 Safari 版本。
