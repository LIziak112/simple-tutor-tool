# 共享发布重复问题核查报告与排重方案

> 状态：**已核查，未修改代码**（核查日期 2026-09-30，行号基于当日工作区，实施时以符号名搜索为准）
> 影响页面：教师端 `/t/shared`（共享页）；关联操作：资源库 `/t/library` 的单条发布与批量发布
> 一句话结论：**发布端每次都无条件写新快照、快照缺少源资源 id、共享列表不做重复识别——三者叠加导致重复快照持续堆积；导入端（共享 → 本地资源库）已有 D18 同 id 合并，不存在此问题。**

---

## 1. 问题现象

教师在资源库把讲义 / 练习单元「发布到共享」（单条或批量）后：

1. 同一份讲义每发布一次，共享目录就**新增一份几乎相同的文件** `标题-登录名-时间戳.md`，没有任何「已经发布过」的拦截或提示；
2. **批量发布重发 = 全部再生成一遍**：勾选 8 项点发布，即使 8 项此前都已发布过，也会再产出 8 份新文件；
3. 共享页对重复**完全无感知**：新旧快照平铺在一起，没有重复角标、没有同源分组，教师无法分辨哪份是最新版，也不知道该删哪些；
4. 长期后果：共享目录文件堆积（列表上限 200 条，超出截断），旧版本快照持续存在并误导他人导入旧内容。

核查时点本机 `data/shared/` 实况：仅 3 份讲义快照、暂无同题重复（判断：近期人工清理过，同目录存在 `backup-20260930` 备份）。但这是机制问题——只要重复发布就必然新增，与是否清理无关。

---

## 2. 根因（代码级证据链）

### 2.1 发布端零排重（主因）

**`apps/server/src/services/shared-service.ts:163-196` — `publishToShared`**

- 被调用即写盘：`mkdirSync` → `writeFileSync(md)` → `writeFileSync(meta.json)`，**没有任何「同源快照已存在」的检查**；
- 唯一的重名处理是**同一秒内**文件名碰撞时追加 `-2`、`-3` 序号（180-184 行）——只防文件名冲突，不防内容重复；
- 伴生元数据 `SharedFileMeta`（47-51 行）只记 `teacherId / loginName / publishedAt`，**不含源资源 id**——发布之后无从追溯这份快照来自哪个讲义/单元。

**`apps/server/src/services/shared-service.ts:258-280` — 批量发布**

- `batch action=publish` 逐项循环调用单项发布实现（快照语义完全一致），同样无已发布检查；
- 前端入口：`LibraryPage.tsx:840-854` 的 `BatchPublishDialog`，确认后对全部勾选项原样重发。

### 2.2 快照缺少稳定的「文件 id」排重键

两类资源的导出内容不对称（`apps/server/src/services/library-service.ts`）：

| 资源 | 导出函数 | frontmatter | 能否事后判同源 |
|---|---|---|---|
| 练习单元 | `exportUnitMd`（1312-1383） | 含 `unit: <单元id>`（1328 行） | **能**——id 即稳定排重键 |
| 讲义 | `exportLectureMd`（1390-1405） | 仅 `kind: lecture`，**无源 id** | **不能**——只剩标题可比（标题可改、非可靠键） |

这意味着即使事后想在共享列表做重复检测，讲义快照也没有精确依据。

### 2.3 共享列表不做任何重复识别

- `apps/server/src/services/shared-service.ts:376-452` — `listSharedFiles`：纯平铺，按发布时间倒序、最多 200 条；摘要提取 `extractSummaryInfo`（331-360 行）只取 `kind / title / questionCount`，不产出任何同源信息；
- `apps/web/src/pages/teacher/SharedPage.tsx`：仅前端搜索（标题/文件名/发布者，58-60 行），无重复标记。

### 2.4 对比：导入端已有排重（重复只在共享侧堆积）

`apps/server/src/services/import-actions.ts`（D18 规则）从共享导入回资源库时：

- 讲义按 **H1 标题**匹配已有项 → 命中则更新版本（106-132 行）；
- 练习按 DSL `unit:` id **全局匹配** → 同 id 合并更新、题目同 id version+1（138-215 行）。

即「重复导入」在本地侧表现为更新而非新建副本。**用户感知到的重复全部堆积在共享目录内**。

## 3. 排重方案建议（供决策，未实施）

### 3.1 排重键放哪：伴生 meta.json（推荐）vs frontmatter

| 方案 | 做法 | 评估 |
|---|---|---|
| **A. meta.json 记录源 id（推荐）** | 发布时服务端本来就知道 `teacherId + 资源id + kind`，往伴生 `<文件名>.meta.json` 里增记 `sourceKind: "lecture" \| "unit"` 与 `sourceId`；发布前扫描现有 meta 即可实现同源判定 | **零 md 格式风险**（md-dsl 解析器与导入链路完全不感知）；讲义缺 id 的问题一并绕开；读取 meta 失败回退 null 的路径已存在 |
| B. frontmatter 增补 id | 讲义导出格式加 `id:` 字段 | 需验证 md-dsl 解析/lint 对未知或新增键的容忍度，且改变导出格式、波及导入往返测试；收益不比 A 大 |

### 3.2 重复发布时的策略（三选一，可组合）

1. **覆盖**（推荐）：命中同源快照 → 删除旧文件（含其 meta）后写新。语义即「更新我发布的版本」，符合快照设计初衷；需注意只允许覆盖**自己发布的**（`meta.teacherId` 校验，复用删除权限口径）。
2. **跳过**：命中即不写，返回「已有快照，未重复发布」。
3. **照发 + 标记**：保持现状写入，但列表接口带出 `sourceId`，共享页对同源多份打「重复 ×N」角标，供手动清理。

推荐组合：**默认覆盖 + 批量发布汇总区分「新建 N / 覆盖 M / 跳过 K」+ 列表对历史堆积提供同源标识兜底**。

### 3.3 改动清单（文件级）

1. `shared-service.ts`：`SharedFileMeta` 增 `sourceKind?` / `sourceId?`（可选字段，旧 meta 自然兼容=不参与排重）；`publishToShared` 入参加源信息、写盘前同源扫描；批量发布返回值区分三类计数；
2. 列表链路：`SharedFileSummary` 增 `sourceId?` 与同源计数；`SharedPage.tsx` 同源角标/分组展示；
3. `packages/contract` 的 shared-api schema 同步字段；
4. **顺带修复（建议同批做）**：在线发布的练习快照在共享页标题显示为**单元 UUID**——`extractSummaryInfo` 用 frontmatter `unit` 当标题（352 行），而发布快照该字段写的是 `unit.id`（`exportUnitMd` 1328 行）。修法与排重同路：meta 增存人类可读标题，列表优先取用。

### 3.4 测试影响（已盘点）

- `apps/server/src/routes/shared.test.ts`、`services` 相关用例中「快照语义 / 文件名」断言需按所选策略更新；
- e2e `shared-publish-import.spec.ts`（发布 → 导入往返）需补：重复发布覆盖、批量发布混合汇总两条链路；
- 新增用例：同源覆盖后旧 meta 一并清除、他人发布的快照不可被覆盖（403 口径）、无 meta 本地文件不参与排重。

## 4. 验收清单（实施后）

- [ ] 同一讲义连续发布两次：按所选策略生效——覆盖后共享页仍只有 1 份且发布时间为新；跳过则明确提示「已发布过」；
- [ ] 批量发布含已发布项：结果汇总正确区分 新建 / 覆盖 / 跳过 数量；
- [ ] 只能覆盖自己发布的快照，他人发布的返回 403（与删除权限口径一致）；
- [ ] 手动放入的本地文件（无 meta）行为与现状完全一致，不被排重波及；
- [ ] 在线发布的练习在共享页显示人类可读标题（非 UUID）；
- [ ] 升级兼容：存量旧快照（meta 无 sourceId）列表、删除、导入行为不变；
- [ ] 发布 → 导入 → 再发布 → 再导入往返内容一致（D16 口径回归）。
