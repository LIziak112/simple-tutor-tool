# 内容模型与导入规范化方案

> 目标：把「单元 / 讲义 / 练习 / 文件」的关系定死为一套规则，让老师不需要理解实现细节就能预判"这个文件导进去会变成什么、叫什么名字、下次重导会发生什么"。
>
> 状态：已实施（task/content-model，2026-09-29）。§7 实施清单 5 单全部落地。

## 1. 一页概念模型

资源库只有三种实体，关系是：

```
资源库文件夹（library_folders）
├── 讲义 lecture —— "讲"的内容，一篇完整讲解正文
└── 单元 unit —— "练"的容器 = 一个练习集，也是布置作业的单位
      ├── 配套讲义（可选，0..1 篇；学生在讲义页底部看到"本课配套练习"）
      └── 题目 question 1..N（同一单元内有序）
```

- **讲义管讲，单元管练，题目住在单元里**；单元↔讲义是可选的一对一配套。
- `practice / lecture / mixed` 是**文档类型**（frontmatter 的 kind），不是存储实体。"练习"落到库里就是"一个单元 + 它的题目"。
- **文件只是导入的载体，不是存储单位**。一个文件按 kind 产出：practice → 1 单元 + M 题；lecture → N 篇讲义；mixed → N 篇讲义 + 1 单元 + M 题。文件本身只进 imports 留档。

## 2. 统一身份规则（核心）

一句话：**文档里声明的名字 = 身份；没声明 = 从文件名派生；身份决定"重导时更新还是新建"；其余情况导入时发 UUID，老师永远不用关心。**

| 实体 | 身份（导入键）来源 | 缺省派生 | 主键 | 再次导入 |
|---|---|---|---|---|
| 题目 | 容器 `id` 属性 | `单元名-序号` | 文本 id | 同 id → 更新（version+1） |
| 单元 | frontmatter `unit:` | **文件名去扩展名** | 文本 id（= unit 值） | 同名 → 合并题目 |
| 讲义 | frontmatter `title:`（新增可选字段） | 第一个 H1 | UUID | 同文件夹同名 → 覆盖正文 |

主键类型差异的解释（老师不需要知道，开发者见附录 A）：题目和单元的身份**写在文档文本里**，必须可从文本对回库；讲义不被文档内部引用，导入时发 UUID 即可。规则统一后，主键类型只是存储实现细节。

三个身份字段各司其职，**不再一字多义**：

| 字段 | 职责（唯一） | 不再承担 |
|---|---|---|
| `unit:` | 练习集的名字 | ——（名即键是明示的规则，见 §8 取舍） |
| `title:`（新增） | 讲义的显示名与导入键 | —— |
| `lecture:` | **配套讲义指针**：声明本练习挂到哪篇讲义（按最终讲义名在同文件夹匹配） | ~~给讲义命名~~（它从来不是干这个的；文档、lint 提示、UI 一律改称「配套讲义」） |
| `topic:` | 单元的知识点标签 | —— |

## 3. frontmatter 最终形态

```yaml
kind: practice | lecture | mixed   # 必填：文档类型
unit: 练习四                        # 可选：练习集名；缺省 = 文件名去 .md
title: 第4讲 有理数                 # 可选（新增）：讲义名；缺省 = 第一个 H1
lecture: 第4讲 有理数               # 可选：配套讲义名（练习 ↔ 讲义的挂接）
topic: 有理数加减                   # 可选：知识点标签
```

讲义命名的完整裁决：

- 单讲义文件（一个 H1）：讲义名 = `title:` > 第一个 H1；
- 多讲义文件（多个 H1）：每篇 = 各自 H1（此时 H1 就是天然的逐篇标题）；若同时声明了 `title:` → lint warning，提示将被忽略；
- `kind: practice` 声明 `title:` → lint warning 不适用；
- 讲义名用上文件名兜底的场景实际到不了（无 H1 本身就是 error），文件名兜底主要服务单元。

单元命名的完整裁决：

- `unit:` 声明 → 用它（现状）；
- 未声明 → **文件名去扩展名**（替代现在的字面量兜底 `"unit"` / "未命名单元"）；
- 因此缺省题目 id 前缀也变为 `文件名-序号`（原来是无意义的 `unit-序号`）；
- 用了文件名兜底时，导入预览给一条 warning 提示"单元名取自文件名"，建议显式声明。

## 4. 匹配与合并规则（不变，仅成文）

| 实体 | 匹配范围 | 行为 |
|---|---|---|
| 题目 | 全局（按 id） | 同 id 更新；文件中缺失的已有题保留；软删题重导即恢复 |
| 单元 | 全局（按 unit 名） | 同名合并；命中已有单元保留其原文件夹 |
| 讲义 | 同文件夹（按讲义名） | 同名覆盖正文；其他文件夹已有同名 → warning |

配套讲义指针解析：同文件夹按讲义名匹配；**匹配不到 → 导入预览给 warning**（LECTURE_LINK_UNRESOLVED，替代现在的静默不关联）。

## 5. 导入交互（配套 UX）

- **选择页 = 一张待导入清单**：粘贴 / 多选文件 / 选文件夹都只是往清单加条目（文件名、路径、大小、可移除、可追加）；粘贴条目文件名就地可改。清单不显示正文。
- **预览页把"文件 → 存储名"亮出来**：批量表格的内容列显示实际名称（`讲义「第4讲」/ 单元「练习四」· 8 题`）而非纯计数；单文件预览顶部统计条同样带名称。
- 规模预检在清单上实时显示；单文件预览保持可编辑、批量保持"改源文件 → 重新预览"。

## 6. 兼容性与迁移

- 遵守 DSL 兼容规则：`title` 为**新增可选字段**，旧文档不受影响；旧版解析器读到 `title:` 会静默剥离（zod strip），优雅降级。
- 存量库数据**零迁移**：不改任何表结构、不改任何主键；仅改"缺省值的来源"和预览展示。
- v1 文档照旧走 v1ToV2 自动转换，落入同一套规则。
- 既有 samples/ 回归样例必须仍解析、渲染一致（硬性规则 12）。

## 7. 实施清单（顺序即依赖）

1. **契约**：`frontmatterSchema` 增加可选 `title`；补契约测试；重跑 `pnpm schema:export`。
2. **解析器**（先补测试再实现，规则 9）：`title` 取值链与两条 warning；`ParseOptions.fallbackUnitId`（仅 frontmatter 未声明 unit 时生效，优先级低于 frontmatter，不影响 reparse 既有路径）；缺省题目 id 前缀随之变化。
3. **服务端**：`analyzeImport` 传入文件名（单文件与批量两条路径都传）；新增 LECTURE_LINK_UNRESOLVED 与"单元名取自文件名"两条导入 warning；动作清单/预览数据带出实际名称。
4. **前端**：选择页重构为统一待导入清单；批量表格与单文件统计条显示实际名称。
5. **文档**：DSL 规范（frontmatter 表、命名与匹配规则成文；若由 gen:spec 生成则改注册表后重跑并提交）、架构文档 §5.1 同步、页面功能清单更新。

每步保持可构建、测试通过（规则 8）；解析器与服务端改动均先写测试（规则 9）。

## 8. 已知取舍（明示，不隐藏）

- **单元名即键**：在库里"改名"语义上等于新建一个单元（旧单元保留）。这是"同名重导合并"特性的另一面；老师改名的正确路径是改源文件的 `unit:` 并接受新旧并存，或删除旧单元。库内改名保持 id 的功能留待有真实痛点再做。
- **多讲义文件的身份完全依赖 H1 文本**：改 H1 = 下一篇新讲义。单讲义文件用 `title:` 声明后不受此影响。
- **配套讲义按名字挂接**：讲义改名后，指向旧名字的练习会挂空（有 warning 提示），需同步改 `lecture:`。

## 附录 A：主键类型为何不同（开发者向）

题目缺省 id 为 `单元名-序号`，单元 id 是题目归队的锚点——两者的身份必须能从文档文本推导并写回文档，故用文本 id；讲义从不被文档内部引用，UUID 即可。统一身份规则（§2）建立后，三类实体的**规则**完全对称（声明 → 派生 → 匹配），主键类型只是实现细节，不再产生行为差异。
