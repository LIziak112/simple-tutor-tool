 判断：脊梁是对的，但它只证明了"展示"这一维
     
  你们最有价值的三条设计，是原文即真相、注册表单一源、gen:spec 
  自动生成规范。这个三角是整栋楼的地基，而且选得对：
     
  - 原文即真相、渲染时再解析，意味着旧内容里本来就写过的指令，等前端补上组件后会自动升级外观，不用重新
    导入。这是全项目最强的架构决定，它让内容对前端永远向前兼容。这条不变量必须像硬规则一样守住。      
  - 注册表到生成规范，让"对 AI 友好"不是额外工作，而是副产品。加一条指令，AI 的规范、提示词、JSON
    Schema、tutor-lint、MCP 同时知道它。
  - 单一渲染入口 + 未知指令优雅降级，让扩展不会炸旧数据。

  所以"是否合理高效"的答案是：合理，且高效。但高效只在"展示"这一轴上被证明过。

  用一把尺子量就看清了。加第 N
  个纯展示指令，成本恒定：注册表加一条、写一个组件、加样例、gen:spec。加第 N
  个可交互、要判分的能力，成本却在涨。填空、提示、手写题各自散落在解析、投影、判分、会话、泄露测试五个
  文件里，全是特判。也就是说，"容易扩展组件"对长相成立，对行为不成立。这正是你们要的第二个目标（老师落
  地可执行的教学方法）卡住的地方。

  机械原因有三个，都可定位：

  - 宿主没消费 Zod 解析结果（评审报告 R04）。组件拿到的是字符串属性表，类型、默认值、校验全丢了，每个 
    新组件自己重新解析属性。这是扩展摩擦的头号来源。
  - 注册表只声明"长什么样"，不声明"能做什么"。指令没有能力面：它消费什么输入、产生什么证据、由谁校验。
  - 四步流程是一条展示管线。它没有覆盖"交互到证据到校验"的竖切。

  精进：把指令从"展示单元"升格为"能力单元"

  核心动作只有一件：让一条注册表声明驱动整条竖切，而不只是渲染。

  第一步，宿主消费 Zod 属性解析。 宿主查表前先跑
  directive.attrs.safeParse，把结果作为类型化、带默认值的 props 交给组件。这是投入最小、收益最大的改动
  ，它让每个组件的属性定义回到契约单一源，也顺带把别名归一的时机问题收干净。先做这个。

  第二步，把 defineDirective 从"外貌"扩到"能力"。 增三个可选面，全部有默认值，老指令零改动：

  ┌─────────────┬────────────────────────────────────────────┬──────────────────────────────┐
  │     面      │                  声明什么                  │            谁消费            │
  ├─────────────┼────────────────────────────────────────────┼──────────────────────────────┤
  │ interaction │ 输入面：无 / 行内空 / 选择 / 手写 / 自定义 │ 宿主，标准形态由宿主提供外壳 │
  ├─────────────┼────────────────────────────────────────────┼──────────────────────────────┤
  │ evidence    │ 产生哪些事件、哪些落库、归属哪个 stage     │ 会话上下文 + 事件表          │
  ├─────────────┼────────────────────────────────────────────┼──────────────────────────────┤
  │ validation  │ 服务端校验器名 + 判定形状                  │ 服务端校验注册表             │
  └─────────────┴────────────────────────────────────────────┴──────────────────────────────┘

  关键在 validation 的判定形状必须包含一个
  unverifiable（无法自动判定，转人工）。这样既守住"判分只在服务端"，又不逼你们做
  CAS。过程题只做规则可判的那部分，剩下明确标"需核对"，交给老师或 AI 事后看。这正是 Astra
  那个"先去括号还是先除三"的坑的正解：不即时判定等价性，只采集证据。

  第三步，把散落的上下文收成一个 DirectiveSessionContext。 现在有
  BlankAnswersContext、DirectiveTelemetryContext 各自为政。合并成一个窄而类型化的会话面：读当前输入、 
  上报证据、请求提示、请求服务端校验。组件不再直接碰 attempt 存储。这就是"Astra 的活动运行时"的正确实 
  现：不是新增一层，而是把宿主几乎已经有的那个上下文补成正式契约。填空已经是它的雏形。

  第四步，gen:spec 多产出一份 capabilities.json。 人类看的规范、给 AI
  的提示词、机器读的能力清单，三份同源。再加一个 MCP 工具 describe_capabilities。这一步才是真正的 AI  
  native 跃迁：今天 AI 会写内容，有了能力清单，AI 会组装教学方法，并且出错可诊断，比如"第 3
  阶段引用了不存在的校验器 X"。这比让 AI
  生成页面代码稳得多，因为它在有限、已声明、可校验的能力内组合。

  做完这四步，"加第 N 个能力"的文件数回到恒定。这是"真实方便地扩展"的可度量定义。

  走向与边界：教学方法即文档，契约即产品

  老师如何真的落地教学方法。 一种教学方法就是一份文档：MD 加指令加声明式检查。老师或 AI
  把它写出来，lint 校验，归档，导入成版本化资产。不是写代码。分步推导用 :::step 表达阶段，每阶段挂一个
  check
  指向校验器；服务端持有判定，客户端永不自行开门。没有证据冻结，任何方法采集的数据都不可信，所以你们  
  T6R 的原稿冻结链是这个方向的前置地基，不是并行支线。它继续走，同时做上面第二步。

  要明确拒绝的。 一是 Astra 那套平行的"活动运行时"，它会和 attempt 快照、事件表、LearningPack
  重复，且与注册表、samples 兼容规则正面冲突。二是再造一套流程 DSL，除非活动类型超过三个且复用收益真实
  成立。三是服务端做中间步骤等价判定，那是研究级问题，还会误杀另一种正确解法。

  开源精神与自由高效，就落在三条不变量上。 契约是产品，不是实现：模型无关，AI
  客户端可换。单进程、SQLite 一个文件、无
  CDN、自部署、数据留在老师机器上。任何人加一条指令，它自动流到 AI、流到对外校验器、流到 dsl-kit      
  分发包，别人拿到就能用。这三点合起来就是"更 native、更自由"的具体含义，不需要再发明新名词。

  落地顺序。 先做第一步（宿主消费 Zod 解析），它是所有后续的解锁点，且能立刻被现有测试覆盖。再做第三步
  （会话上下文收编）。然后第二步（能力面）。最后第四步（能力清单）。每一步都保持恒定成本、可独立验收，
  也都能沿用你们既有的"先失败测试再实现"和 samples 回归。

  一句话收束：保留脊梁，把注册表从"长什么样"扩成"能做什么、留下什么证据、谁来校验"，让新能力沿整条竖切
  保持恒定成本。教学方法因此成为可版本化的文档，AI 因此从写内容升级为组装方法。
