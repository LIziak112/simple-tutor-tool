# 题目草稿功能：独立评审与建议方案

评审日期：2026-10-05。评审对象：[外部评审请求](题目草稿功能-外部评审请求.md)、[功能方案](../题目草稿功能方案.md)、[Phase 6 任务清单](../Phase6任务清单.md)，并抽查仓库现有实现。

本报告是设计评审和替代方案建议，不代表原设计已经修订，也不是实施授权。本轮未修改契约、数据库或功能代码；未运行功能测试、未做 iPad 真机验证。浏览器相关结论区分官方文档、项目问题报告和本报告的工程建议。

## 结论

**建议修改后采纳，保留技术基础，但不要按当前 D6.1、D6.7 和附录 B 原样执行。**

独立草稿区、复用 InkSurface、矢量与图片双保存、隔离作答本地仓、文本加图片导出、复用 LearningPack，都是适合现有项目的选择。无需推倒重来，也无需先引入新的手写库、云服务或服务端无头浏览器。

目前方案能较好实现“学生有地方写、笔迹能保存、可以把图交给 AI”。但要实现用户更重要的目标——“老师判断这一次哪里错了、后来是否真正学会”——有三个关键缺口：

1. **历史证据不可靠。** 全局可编辑草稿会覆盖第一次作答的演算，时间戳无法还原被覆盖内容；看解析后的订正可能被误当成独立作答过程。
2. **导出并不天然便捷或完整。** 单题复制文字再逐张下载图片仍需用户手动配对；自研 DSL、题目图表和自部署媒体地址也未必能被外部模型理解。ZIP 中的 Markdown 图片引用不等于图片已经成为模型可见输入。
3. **诊断输出缺乏证据约束。** 当前提示词要求指出错误步骤，却没有要求先核对笔迹、标记看不清处、区分原稿与订正、说明无法判断的部分。容易把猜测写成“掌握情况”。

**优先把“每次作答留原稿、导出材料对应、诊断可核对”做完整，再加合成图片和题干标画。**

## 一、从真实需求反推产品边界

| 需求 | 当前方案判断 | 必要调整 |
| --- | --- | --- |
| R1 演算与历史复盘 | 写字和保存可行；“当时的过程”可能被覆盖 | 按次留存原稿，后续订正与原稿分开 |
| R2 左题右稿／下方草稿 | 方向合理，固定断点和等高规则仍需验证 | 按题卡可用宽度判断分栏；高度统一逻辑单位 |
| R3 笔写、手指滚、手掌不误触 | 适配器已有可复用基础 | 多题、多画布、首次落笔、旋转和卸载仍须真机回归 |
| R4 单题与整套导出 | 整套管线可复用；单题材料缺少完整交付形态 | 提供预配对的单题包，保留复制文本／下载图片快捷入口 |
| R5 学习证据链 | 目前最欠缺的部分 | 明确作答批次、题目版本、笔记阶段、证据缺失状态和诊断边界 |
| R6 题干标画 | 附录 B 复杂，位置保证不充分 | 单独后置；自由手绘优先固定底图，文本高亮另走语义锚定 |

还要明确“过程”的含义：当前矢量文档保存的是最终留下来的笔画。整笔擦除、撤销、清空以后，被删除的内容不会出现在最终图中；笔画时间 `t` 是本笔内相对时间，并不是整题思考时间线。因此可以承诺“回看保留下来的演算”，不能承诺“完整还原全部思考与改错经过”。不做回放是合理的，但产品文案和 AI 提示词应准确表达这个边界。

## 二、按请求 §7 逐条回答

### 1. 归属模型：全局单份，还是按 attempt 冻结？

**结论：学习诊断所用的原稿必须关联具体 attempt；全局笔记可以存在，但只能作为持续编辑的学习层。**

具体反例：

```text
第一次作答 A：解法错误，选 A → 交卷
看解析后：在同一草稿里擦掉错误步骤，写正确解法
第二次作答 B：做对 → 再修改同一草稿
老师导出 A：第一次错误答案 + 最新正确草稿
```

AI 可能误判为“思路正确，最后误选”，真正的概念错误已被擦掉。增加 `updatedAt` 最多说明草稿较新，不能恢复 A 的原稿，也不能证明新草稿具体属于哪一次作答。

推荐产品呈现：题目笔记本汇总“第一次原稿、第一次订正、第二次原稿……”。答题页编辑本次草稿，结果页默认显示本次原稿，学生点击“添加订正”另开记录。这样“同一道题跨练习可回看”与“每次过程不被覆盖”可以同时成立。

如果需要严格保留已经选定的“全局一份可继续编辑”体验，折中做法是：保留全局工作稿，并在每次交卷时记录不可变版本引用。它同样需要按 attempt 的检查点，不能仅靠导出时间戳解决。

重练时不宜默认把上次订正稿铺在当前画布里；它可能已经写着答案。默认新空白草稿，历史笔记显式查看；是否看过提示、历史解法等已知信息应与诊断材料一同标明，未知则写“未知”，不要推定完全独立完成。

这里不需要笔画事件溯源或无限版本历史。最低限度保留每次提交边界的原稿，以及后续独立订正记录就足够。学生若希望老师看到尚未交卷时发现的错误，可以划掉错误步骤再往下改，而不一定擦除；这是可选的学习习惯建议，不能假设最终草稿已经保留了所有错误尝试。

### 2. 交互形态：分栏、比例和 sticky 是否合理？

**结论：独立草稿区是合适的第一版；不建议一开始做可拖拽分栏。**

55/45 可以作为试验起点，但应按题卡容器的实际可用宽度判断，而不只看 viewport 是否超过 1024px。页边距、题卡内边距、应用最大宽度、iPad 分屏都会使真实画布更窄。注册表中三个布局值可保留，布局解析输入应表达容器约束；全屏、浮窗以后仍需要各自生命周期和布局实现，“加注册表项就零改动”不应成为承诺。

侧栏模式建议分离“题卡高度”和“纸张高度”：草稿外框可与题目视觉等高，但持久化纸张高度必须按逻辑宽 1000 的坐标系表达。不能把 grid 拉伸得到的 CSS 高度直接当文档高度。缩小画布也不能裁掉已有笔画，至少保留到最大笔画 y 坐标加留白。

当前工具条含笔色、粗细、荧光笔、橡皮、撤销、重做、清空、布局、背景等，在 45% 侧栏里难以全部保持 44px 触控目标。第一层保留笔、橡皮、撤销、更多；颜色、粗细、背景放入更多面板，避免工具条占掉书写区。

长草稿使题目离开屏幕的问题确实存在。可以在短题干时试验局部 sticky，长题干超过视口时关闭；不要整块无条件 sticky。第一版更简单的方案是保留页面单一滚动，加“回到题干”按钮；长时间书写的专注布局可后置。

不建议“所有历史有笔迹题目进入页面都自动展开并挂载画布”。先显示轻量缩略图／墨点，用户展开当前题时再挂载引擎。渲染一套题时，多画布内存消耗比单画布尺寸更容易被忽略。

### 3. 同步窗口：2s 防抖、离页保存与时间戳合并够不够？

**结论：可以作为网络优化，不能单独构成防丢承诺；客户端时间戳不适合作为冲突裁决依据。**

“丢失窗口”必须分开看：

- 本机：如果每笔结束后本地写入有 300ms 等待，且进程在事务完成前被杀，最后笔画可能丢失；正在书写但尚未提交的一笔也可能丢失。这里的 300ms 只是计划等待值，不是严格损失上界。
- 服务端：停笔 2s 才上传，连续书写可能一直没有停够 2s；叠加图片编码、上传耗时和失败重试，不能说“最多只丢两秒”。如果没有最大等待时间，服务端落后窗口可以持续很久。
- 离页：`visibilitychange` 时的 PUT 和 `pagehide` 中异步 IDB 写入都只是尽力执行，不能保证浏览器留下时间完成。官方文档也指出移动端离页事件可能不触发。[MDN：sendBeacon 与页面生命周期](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/sendBeacon)

推荐机制：每笔完成就进入本地持久队列，不等 PNG；本地写事务按顺序执行；网络维持 2s 防抖并增加最大等待时间，例如 10–15s 作为待真机验证的初值；恢复可见、恢复网络、重新进入题目时补传。未完成的本地写入要显示“保存中”，本地失败不得显示“已存本机”。持久 IDB 也可能因存储压力等被清理，不能成为唯一长期存档。[WebKit：存储策略](https://webkit.org/blog/14403/updates-to-storage-policy/)

请求中“multipart 不可用 beacon”需要纠正：`sendBeacon` 接受 `FormData`，但它只发 POST、没有业务回执、排队数据约 64KiB，不能兜底最大 2MiB 的整份草稿；`fetch keepalive` 也不应当成大文件退出上传保证。当前无需为此专门新增 beacon 通道。[MDN：sendBeacon 参数和限制](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/sendBeacon)

冲突建议使用服务端整数 `revision` 与客户端 `baseRevision`：版本一致才覆盖，旧版本请求返回冲突。客户端时间只用于显示；服务端 `savedAt` 表示到达时间。两个设备都改了同一文档时，保留两份冲突副本并让用户选择，不自动合并笔画，也不自动按墙上时钟覆盖。橡皮、撤销和清空使简单拼接笔画尤其不可靠。

同一客户端还要保证：一次只有一个上传在途；每次上传绑定固定文档版本和对应 PNG；回执只清除该版本 dirty；新变化继续排队。收起题卡或离开页面后，队列仍应能根据已保存矢量生成快照，不应依赖已经销毁的 canvas。

### 4. 存储预算：2MiB 和 PNG 倍率是否合理？

**结论：2MiB 可以作为初始保护阈值，但目前没有足够数据证明它适合作为可用性边界；不要固定所有图片都 DPR2。**

PNG 体积受笔迹密度、背景、荧光笔、画布空白、尺寸和编码影响。未做真机样本测量，不能给出可信的“每题通常多少 KB”。应测短、中、长草稿及密集格线，记录矢量压缩大小、PNG 大小、编码耗时、峰值内存、最小字的可读性，再定阈值。

例如宽 450 CSS px、高 1350 CSS px、DPR2 的画布为 900×2700，单个位图 RGBA 约 9.3MiB；编码和克隆期间可能同时存在多份位图。PNG 文件小，不代表浏览器内存消耗小。

归一化宽 1000、高 3000 的纸张按 2 倍导出为 2000×6000：约 12M 像素、单个位图约 45.8MiB。即使面积低于请求提到的约 16.7M，长边仍可能触及设备限制。MDN 明确提醒最大尺寸依浏览器和环境变化，并列出 iOS 4096×4096 限制；因此不要把固定面积阈值当跨版本保证，应限制面积、长边和多画布总量并真机验证。[MDN：canvas 最大尺寸](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/canvas)

建议保存／导出按用途处理：矢量是可恢复的主数据；PNG 是用于回看和分析的派生表现。回看显示缩略图，分析取足够清晰的原图；长草稿可按顺序导出切片，保留少量重叠和坐标映射，避免大模型端把一张极长图缩成无法读的小字。不能为压到 2MiB 无限降低清晰度。

超过限额时先裁掉无笔迹的空白、调整 PNG 尺寸，仍超限则保留本地原稿并明确显示未同步原因。不能上传失败后建议学生擦掉演算，也不能静默丢弃矢量。第一版可以保留矢量＋PNG 的一次提交，但若图片生成经常失败，应允许矢量先保存并显式记录图片待生成状态，后续再补 PNG。

### 5. AI 包格式：Markdown、LaTeX 与 PNG 是否合适？

**结论：这个组合适合作为主格式，但不能称为跨模型的“最优格式”；应补齐题目视觉信息和关联清单。**

推荐同时提供：便于人工和聊天使用的 `review.md`，用于准确配对的 `manifest.json`／LearningPack 字段，以及实际图片附件。无需把 LaTeX 全部转 Unicode，分式、根号、上下标和矩阵会因此丢掉结构；保留原数学表达式更稳妥。

当前还有两类材料缺口：

- 项目 Markdown 包含自研 DSL。外部模型不一定理解折叠、图表等指令；图表配置和源文字也不等于学生实际看到的图形。
- 单题文本若只有题干和“选择 A”，却没列 A/B/C/D 的选项全文，就不能稳定解释错误；自部署媒体地址外部模型通常也无法直接获取。

所以普通文本题导出题干＋完整选项即可；几何图、函数图、图片、表格和交互题应带已冻结的可读视觉附件。原 DSL 可作补充材料，不能要求模型靠它恢复整个页面。不要为了所有题目都截图而依赖截图完成后才能导出基本文本与草稿。

每份草稿附件至少明确：包内记录号、具体作答批次、题目版本／快照引用、原稿或订正、版本号、采集与保存时间、完整／缺失／待补传状态、文件路径和尺寸。学生包仍只含其已有权限的题目投影；教师包可按模块加入标准答案、解析和行为数据。

`[scratch-q3.png]` 只是文字，Markdown `![](scratch-q3.png)` 也只是引用：用户还需要把真实图片上传给目标模型。ZIP 是否自动解包并把图作为视觉输入，取决于客户端，必须用实际目标工具验证，不能只测“ZIP 下载成功”。

AI 提示词应要求：先识读可见演算，列看不清处；引用图号和步骤；指出最早能被证据支持的错误；区分后续连带错与另一个独立错误；材料不足则要求澄清，不能补写学生没写的过程。错误类目可以包含读题／建模、概念、运算、表达和最终填答，但无法确定时要明确说无法确定。

### 6. LearningPack 扩展还是另建轻量通道？

**结论：保留一套数据装配与权限投影，允许两种入口。**

整套导出继续复用 LearningPack，长期维护成本较低。单题入口则应绕过五步向导，使用预设配置一键下载／分享本题材料；已有 `archiver` 可以生成只有一题的 ZIP，不必引入客户端 ZIP 库。

单题快捷按钮可以继续提供“复制文字”和“下载图片”，但它们不宜作为唯一完整出口。默认给出已配对的一题包，界面提示“文字已复制，还需上传 1 张草稿图”这类明确状态。多人、多次作答的批量包则保留化名和范围确认流程。

应抽取的是“题目证据装配、角色投影、素材清单和共享提示词”，而不是再写一套 student 客户端、teacher 客户端、MCP 各自拼字段的业务逻辑。UI 与 MCP 从契约中的模块和目标信息生成可共享部分；此次可以局部整理，没必要先建通用导出插件框架。

仓库已有一个更深的关联问题：`export-service.ts` 的 `content.questions` 按 questionId 取所选范围中最新提交快照，而 `attempts.responses` 包含历次作答。若老师改过同一 id 题目的数值或选项，仅新增 notes PNG 会使旧作答配上新题干。逐题诊断需要每条作答引用对应的题目快照／内容 hash，按内容去重，而不是只按 questionId 去重。这个问题应与草稿导出一起解决。

还应确定答题过程中题目被编辑的处理规则：本次草稿关联的是学生书写时看到的版本，不能仅在交卷时读取当前库版本便假定两者一致。可以固定本次题目版本，或发现版本变化时明确处理；学生端导出的引用与 hash 只针对其可见内容，不暴露完整教师快照中的答案字段。

### 7. html-to-image 在 iPad Safari 上是否可靠？

**结论：可用于按需导出，但必须通过前置真机试验；不适合当草稿保存成功或证据成立的前提。**

官方 README 说明它通过 DOM 克隆、内联字体与图片、SVG `foreignObject`、canvas 完成截图，提到受污染 canvas 和超大 DOM 的限制；它也写明做过 Safari 测试。因此不能笼统说它完全不支持 Safari。[html-to-image 官方 README](https://github.com/bubkoo/html-to-image)

同时，项目有 iOS 下载／分享图片空白的具体报告。这是风险线索，不是本项目必然失败的证明，但足够支持先拿本项目真实 KaTeX、图表、长题卡做试验。[html-to-image：iOS 空白图片报告 #556](https://github.com/bubkoo/html-to-image/issues/556)

建议使用独立导出版式，而不是直接截图正在交互的题卡：固定宽度和白底；去掉工具条、编辑按钮、选项控件；把学生选择转成静态文字；折叠内容按预设处理；关闭图表动画并调用现有图表导图能力；等待字体和图片解码完成；避免继承 overflow 裁切和 sticky 位置。

全量缓存 KaTeX 字体 CSS 可以减少重复工作，但并不消除字体度量、外部图片、异步资源与大内存问题。canvas 先转图片只解决其中一类问题，不等于解决全部 `foreignObject` 风险；dataURL 本身也会增加内存开销。

降级出口优先保证：题目文字＋题目已有图片／图表导图＋草稿 PNG 可以分别导出；完整合成图失败不影响保存。如果希望人看材料，可另提供打印友好 HTML，由用户通过系统打印导出 PDF，不需要服务端无头浏览器；其分页与图片完整性也需单独验收。换一个同样基于 `foreignObject` 的库不会自动解决架构性风险。

此外，自部署环境还有遗漏：局域网普通 HTTP 下不应承诺 Clipboard API 可用；Safari 的剪贴板要求安全上下文和用户手势，先 `await fetch` 再写入可能失去手势资格。可以预取图片，或在点击事件内用 Promise 支持的 ClipboardItem 组织写入，并始终提供下载／手动复制兜底。[WebKit：Async Clipboard API](https://webkit.org/blog/10855/async-clipboard-api/)、[WebKit：异步 fetch 后 write 失败与处理方式](https://bugs.webkit.org/show_bug.cgi?id=222262)

### 8. 题干标画：实时层＋冻结快照兜底是否可靠？

**结论：不建议第一版采用；“匹配布局”不是可保证的几何一致条件。**

side／below 相同、宽高相同，也不能证明文本换行、公式位置和图表内容相同。字体加载、内容版本、浏览器缩放、字距、DSL 渲染版本、fold 状态、异步图片和图表状态都可能改变位置。要继续实时编辑，就需要检测这些状态、追踪失效、避免在布局变化后抓到已经错位的快照，复杂度远超“有一张兜底图”。

覆盖层的穿透方式也不充分：若画布是事件的顶层 target，`event.target.closest('input, …')` 找到的是画布自身，不能直接识别下面的输入框；需要额外命中测试或事件路由。即便允许手指点选控件，用笔落在控件上到底应圈注还是操作控件，仍需定义产品语义。

两条更可靠的路径：

- 自由圈画／划线：在标注模式里使用一份固定宽度的题干底图，矢量标注与底图一起等比显示；原交互题仍用于作答。只需固定一次底图，不必每次保存都重抓 DOM。若现有截图管线无法可靠生成底图，先不发布自由标画。
- 文本高亮／批注：关联具体题目版本与文本引用，保存 exact、prefix、suffix 等，再在当前排版中重新定位。W3C 的 TextQuoteSelector／TextPositionSelector 可借鉴，但公式、重复文本和自研 DSL 仍需要专门处理；不应宣称它能解决任意自由手绘圈的位置。[W3C：Web Annotation Data Model](https://www.w3.org/TR/annotation-model/#text-quote-selector)

“像截图标注”的视觉成本小于“圈错位置却没发现”的证据成本。可以将固定底图嵌入题卡，使界面自然，不必做成另一个截图管理工具。

R6 既然优先级较低，可以独立后置；但未来若诊断使用这些标注，其底图和版本应能一并导出，不能长期成为 AI 看不见的证据。

### 9. 整体盲区与过度／欠设计

**欠设计主要在证据边界、导出完整性和恢复机制；过度设计主要在题干覆盖层与过早细化体验选项。**

需要补充的具体边界：

1. **原稿、订正、重做混淆。** 同一道题做对、同题背答案做对、看解析后补写正确解法，不能被表示成同一种“掌握”。行为计数只能提供线索，不能证明学生实际思考方式。
2. **题目编辑和软删后的历史。** 原设计接口要求当前题存在且未删；但已有作答快照允许历史题目软删后回看。按历史作答取草稿应由 attempt 归属与快照授权，不依赖当前 questions 行。
3. **创建权限过宽。** 仅校验教师域内题目存在会允许学生探测并对尚未开放题目创建记录。无需把它夸大为答案泄露，但有存在性探测与磁盘写入面。新建应基于获授权的作答／可见题；已有个人笔记可按明确策略继续访问。
4. **背景未进入草稿 PNG。** 当前 `exportPng()` 是白底加 canvas 位图；CSS 格线不会自动进入 PNG。既然要求回看／导出同背景，应复用一个确定性的背景＋笔迹渲染函数，并验证其结果。
5. **文件与数据库一致性。** 单文件 tmp→rename 不等于 gzip、PNG、DB 三者事务一致。宜写不可变版本文件，确认文件就绪后事务切换记录引用；垃圾回收只能清未引用旧版本，不能清提交快照。备份也必须覆盖这些文件与引用。
6. **收起后的保存。** 现有上传控制器依赖活着的引擎导 PNG。只复刻这个模式会使草稿收起后的 dirty 数据无法补传；笔记持久队列需要独立于 React 题卡挂载状态。
7. **失败被隐藏。** 结果页 `onError` 隐藏图片会把“原稿读取失败”伪装成“没写草稿”。应区分无原稿、未同步、缺文件和读取失败，并提供重试或文字状态；导出也应列缺失项。
8. **化名并非图像脱敏。** 文件名和 JSON 化名不能去掉学生手写的姓名、班级或联系方式。预览中应能看到实际导出图片；不要把元数据匿名化表述成图片已匿名。
9. **学习闭环尚不完整。** 增加轻量“我卡在哪里／这次错因是什么”的可选反思，以及教师待确认诊断，价值高于大量新工具条。之后用无提示的变式题／延后再测验证是否改善，不凭单张图生成精确掌握百分比。

仓库抽查还发现请求文档的两处代码事实需修正：上传 hook 实际在 `apps/web/src/features/attempt/use-ink-upload.ts`；当前 atrament 适配器可见合并采样与逐点绘制，但未见 `getPredictedEvents()` 或显式湿干双层画布实现。因此 §3 的“已全部在引擎内”不应作为已经验证的事实。这不阻碍复用现有引擎，只要求实施前把事实描述校准。

### 10. 契约与演进：noteDoc v1 与题干标画是否要合并？

**结论：未发布的 v1 带纸张高度和背景合理；版本、归属和同步元数据需要补足；题干标画不要塞进同一个可变文档。**

文档内容与记录身份建议分开：内容包含逻辑宽度、高度、背景和笔迹；外层记录包含所属学生／教师域、attempt、题目版本引用、original／correction 阶段、revision、保存时间和附件状态。学生上传不能自行指定归属，也不能用 client 时间决定服务端是否接受更新。

`padHeightLogical` 要明确宽 1000 基准，默认值统一；背景类型扩展必须定义旧客户端无法识别时的回退。矢量解析成功不代表可安全渲染，还应规定笔画数、点数、单笔点数、坐标和尺寸界限，避免在解压字节限制以内制造极高渲染成本。

题干标画多出底图、底图版本、资源与标注坐标的生命周期；它应作为独立的关联附件／子文档。可以在同一“题目笔记本”中显示，却无需与空白草稿绑成同一次 2MiB 覆盖上传。

正常新增可选字段可以继续 v1 并提供默认值；改变坐标定义或文档语义才需要新版本和读取升级。contract 是单一来源，客户端 IDB 旧记录也须有校验与迁移，不能只考虑服务端 JSON。原有已发布 InkDoc 不应为了笔记而直接改变必填形状。

## 三、建议方案：按次留原稿，按题汇总笔记

### 3.1 用户体验

```text
答题页：本次草稿 → 自动本地保存／后台同步
交卷：题干快照 + 学生作答 + 本次草稿版本引用
结果页：只读原稿 → 添加订正（新记录，不擦原稿）
重练页：新的本次草稿 → 可主动查看历史笔记
题目笔记本：第一次原稿／订正／第二次原稿……
导出：本次材料、原稿与订正对照、整套记录
```

原稿与订正可以沿用同一个 InkPad 编辑组件；两种记录复用上传和存储原语，不需要两套手写系统。手写题可把现有作答 ink 作为原稿证据来源，第一版不必再挂第二个画布；只要教师和导出端都能消费它。

### 3.2 最小数据组织

以下是待确认的设计草案，正式实施时先在 `packages/contract` 定义 Zod schema，再生成迁移，不直接照此手工改库。

| 概念 | 作用 |
| --- | --- |
| 题目笔记索引 | 以学生及教师域内 questionId 汇总历史；只作导航，不能替代作答证据身份 |
| 本次草稿记录 | 关联 attemptId、questionId、题目版本；未交卷时可编辑 |
| 草稿版本附件 | 成对的矢量与 PNG／待生成状态；文件不可变，记录内容 hash、逻辑尺寸与渲染版本 |
| 提交证据引用 | `(attemptId, questionId)` 指向交卷边界所选的确定版本；后续编辑不能切换它 |
| 订正记录 | 指向来源 attempt，阶段为 correction；保存新的版本，不修改 original |

可以只维护一个当前编辑头，加必要的提交／订正检查点，不保存每一笔永久版本。已有冻结引用的附件永不覆盖；无内容变化则复用附件，减少存储重复。题目快照也可按内容 hash 去重。

如果选择全局工作稿折中，第三、第四项仍必须保留，而且同时做两次练习时要明确哪个工作稿版本属于哪个 attempt。这也是按次草稿更容易解释的原因。

### 3.3 交卷与断网的一致性

“草稿不参与判分”应保留；“草稿完全不与交卷边界协调”应修改。提交正文无需携带整份笔迹，可以只携带版本引用和状态；判分输入保持现有答案。

交卷前客户端先固定本次原稿候选版本，完成本地落盘，并尽力上传。服务端在提交事务内核验版本归属并锁定引用。若网络导致原稿尚未同步，不能静默改用旧图或最新全局图：允许答案按既定产品规则交卷，同时明确标记原稿未完整同步。

若支持交卷后补传原稿，补传必须属于交卷时固定的候选记录／内容 hash，走专门的待补全状态；不能把之后订正的文档放回 original。恢复后只补这个候选版本。无法恢复则保留缺失标记，导出不编造替代证据。

这是教学记录的内部一致性设计，客户端采集时间和离线候选都不是防篡改考试证据；本功能无需为此建立考试监考体系。

### 3.4 导出形态

单题与批量共用证据装配服务，用户操作路径不同：

- 单题：“导出本题”直接使用当前 attempt 及可见范围，下载一题包；复制文字／图片是快捷选项。
- 原稿与订正对照：明确分节，原稿在前，订正在后；保留各自时间、题目快照和证据缺失状态。
- 批量：“导出错题与过程”预设范围与诊断目标，跳入 LearningPack 预览；也可选答对题，用于发现猜对或过程错误。
- 人看：合成图片作为方便分享的附加出口，长稿分页；打印版作为另外的人工导出选项。

示例文件结构：

```text
review.md
manifest.json
questions/q001/stem.md
questions/q001/stem-figure.png       # 仅图形题需要
evidence/q001-attempt01-original.png
evidence/q001-attempt01-correction.png
```

文件名使用包内编号／化名，不把真实 studentId 放入对外文件名；元数据延续现有隐私策略。manifest 区分“没有写”“有本地未同步稿”“图片生成失败”“文件缺失”，不能统一省略。

### 3.5 让分析真正落到“哪里错”

建议提示词按以下顺序组织，具体 JSON 输出可作为后续契约，不必第一版强制所有模型遵守：

1. 列出收到了哪些题目、选项、原稿、订正、作答结果；标记缺失或难识读材料。
2. 转写与判断有关的可见步骤，保留学生实际写法；看不清处标为未知。
3. 先检查每步是否正确，再指出最早可确定的错误，引用图号、行号或相对区域。
4. 将“观察到的事实”和“可能的原因”分开；不同原因无法区分时给出一道澄清问题。
5. 说明原稿、订正、重练之间发生了什么变化；仅订正正确不能推断独立掌握。
6. 给一个最小修正提示和一道用于区分错误原因的变式题；列出老师需要确认的地方。

可选的学生反思：“我卡在把条件转成方程”“算到这里不确定”“我看懂了解析，但还不能自己做”。可选自评应与客观证据分栏，不能当成能力分数。

示例：

```text
观察：原稿图第 2 行由 2(x+3)=10 写成 2x+3=10。
定位：最早可见问题在展开括号；常数项没有乘以 2。
推测：可能未理解分配律，也可能是漏写，现有材料不能区分。
澄清：请独立展开 3(y+4)，并解释每一项为什么这样写。
复核：订正稿展开正确；需要另一道无提示题确认是否能独立迁移。
```

这类输出可以支持教师判断；直接输出“分配律掌握 60%”没有对应测量依据。AI 建议应可由学生／老师核对，不进入自动判分链路。

## 四、建议调整排期

| 阶段 | 交付 | 为什么排在这里 |
| --- | --- | --- |
| 开工前修订 | 原稿归属、题目版本引用、冲突和补传状态、导出权限 | 会影响契约和迁移，不能等实现后再补 |
| 小范围技术验证 | iPad 写字／滚动；真实 KaTeX＋图表截图；图片复制／下载；内存和大小测量 | 截图可失败降级，但要提前知道限制，不把未经验证方案锁成前提 |
| 第一批核心交付 | 本次草稿保存、只读原稿、教师查看、单题完整导出 | 完成“记录→查看→交给人／AI分析”的最小闭环 |
| 第二批学习闭环 | 订正、历史对照、LearningPack 批量、证据化提示词与反思 | 支持判断错因与重练改善 |
| 第三批体验增强 | 合成图、专注布局、题干标画 | 不影响原稿可信和基本导出 |

原清单把教师查看放在 T6.10，单题评析的教师草稿附件还依赖它补齐。对于一对一教师产品，建议教师只读查看与学生原稿回看一起交付；把题干标画后置更符合 R5 的优先级。

## 五、验收应重点证明什么

下面是建议新增到实施计划的测试点，不是本轮已执行结果。

1. 第一次错误原稿交卷后，订正、清空、重练均不改变第一次原稿文件和引用。
2. 同 id 题目改数值／改选项后，旧作答导出仍使用旧快照，草稿与该次作答对应。
3. 题目软删或课程失权后，按允许的历史访问策略仍能回看已有个人原稿；不能因此新建未授权题目记录。
4. 两设备及同设备两标签页改同一文档，旧 revision 不会覆盖新版本；冲突副本可恢复。
5. 上传 A 时产生变化 B，A 回执不清除 B；收起题卡后仍能补传 B；账号切换不会续传到另一个学生。
6. 写字后立即切 App／锁屏／杀 Safari，重进能恢复已完成的本地事务；本地存储故障明确显示，不能假称已保存。
7. 交卷时上传失败，原稿状态明确，补传只接固定候选版本，订正不能替换原稿。
8. CSS 背景、空白裁剪、最大高度、横竖屏缩放都在实际 PNG 中正确；导出缺图必须列明。
9. 学生未公布答案时，文本、图片、manifest、ZIP、失败响应均不泄露参考答案、解析和未获授权提示；测试涵盖填空 `[[答案]]`、正确选项标记和历史引用路径。
10. 跨教师同 questionId、跨学生、跨 attempt 访问都被隔离；新接口走 assertNoLeak，域外访问不暴露存在性。
11. iPad 普通 HTTP 和 HTTPS 分别走通导出兜底；复制失败不妨碍手动复制／下载；公式和图表真的可读，不能只验 PNG 魔数。
12. 将一份单题包与一份批量包实际交给目标模型，确认其真正看到图片，回答能够引用原稿步骤；缺证据样本必须回答不能确定。

实施仍遵守仓库“计划确认→TDD→质量闸门→真实验证→合并”流程；涉及学生载荷与导出投影要纳入安全审查。此评审不替代这些实施闸门。
