二、需要修的（按优先级）
1. 🔴 唯一的真 bug：提示删减后 hintsRemaining 为负（hint-service）

属实。hint-service.ts:166-170 取历史已解锁集合 opened 直接算 hintsUsed = nextOpened.length，L208 hintsRemaining: hints.length - hintsUsed。

复现路径：草稿期学生解锁了全部 5 条提示 → 教师编辑题目把提示删到 2 条 → 学生再请求任一提示 → hintsRemaining = 2 - 5 = -3，违反契约 attempt.ts:284 的 min(0)，前端 apiResponseSchema 解析直接失败，提示功能打挂。

改法：openHint 里对历史集合先收敛再计算——

const opened = openedIndexesOf(existing?.hintsOpenedJson ?? null)
  .filter((i) => i < hints.length); // 教师删减提示后，越界序号收敛掉

回写 hintsOpenedJson 时用收敛后的集合，存量脏数据随之自愈。按硬性规则 9 的精神，先在 hint-service 测试里补一条“解锁全部→删减→再请求，hintsRemaining ≥ 0 且 hintsUsed ≤ hintCount”的用例再改实现。

2. 🔴 契约测试把“course 来源 unitId=null”锁成合法（attempt.test.ts）

属实。attempt.test.ts:60-66 的 SUMMARY_COURSE_SECOND 展开 SUMMARY_DRAFT（unitId: null）却没覆写 unitId，L114 的 parse 照样通过——与契约注释“course 来源恒有值”（attempt.ts:74）直接矛盾。服务端目前确实会写 unitId（attempt-service.ts:106-108），所以这是“测试未守住不变式”而非线上错数据。

改法（两步，第二步可选）：

fixture 补 unitId: UNIT_ID；如想锁反面样例，另加一条“assignment 来源 unitId=null 可解析”的断言；
顺手把同根因的 🟢（summary 无交叉不变式）一起收掉：给 attemptSummarySchema 加 superRefine，锁定“course → courseId/unitId 非空且 assignmentId 空；assignment → assignmentId 非空且 unitId 空”。改了 contract 要重跑 pnpm schema:export 并提交（AGENTS.md 规则）。
3. 🟡 hasAttempts 语义与文案脱节（三处同步）

属实。服务端 course-service.ts:969 与 courseHasAttempts 均为“有作答或有作业”，但契约注释（course-api.ts:58）只写“关联作答记录”，前端 CoursesPage.tsx:199、285、327 三处文案都是“有作答记录”。只布置了作业、零作答的课程会挂一个与事实不符的“有作答记录”徽章。删除守卫本身是对的，不用动逻辑。

改法：三处文案改成“有作答或作业”（如“该课程已有作答或作业，不能删除；请改用归档”），契约注释同步。注意 course-api.ts 在工作区有未提交改动，改在其上即可。

4. 🟡 草稿提示回显不过滤软删题（hint-service，与真 bug 同文件）

5. 🟡 取卷（paper）与详情/存答的鉴权口径割裂（attempt-service）

属实，但影响比报告描述的小——我核实过前端根本没有消费任何取卷接口：fetchAttemptPaperApi（api.ts:687）是死导出，答题页走 detail 草稿视图（自带题目）。另外我还发现报告没提到的一点：attempt 侧的 requireAssignmentVisible（attempt-service.ts:362-371）没过滤 removedAt，与其注释宣称的“与旧 paper 接口同口径”不符——实际效果反而符合“被移出学生已建作答仍可继续”的口径。真正割裂的场景是作业软删后：draft 学生详情/存答 200、取卷 404。
